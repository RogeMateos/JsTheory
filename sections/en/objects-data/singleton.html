Singleton Pattern in JavaScript

1) What is a design pattern?

A design pattern is a "recipe" or repeatable solution for common software design problems.

  • It's not a library
  • It's not a mandatory rule
  • It's a well-known way to solve something that tends to repeat

2) What problem does Singleton solve?

Singleton aims for this:

  • ✅ That only one single instance of a class exists during program execution
  • ✅ And it usually also provides a single point of access to that instance

Typical examples where it makes sense:

  • Logger (log recording)
  • Global configuration (read-only)
  • Cache
  • API / DB client (with caution)

3) Base case: normal class (NOT Singleton)

Let's simulate a very simple "session".


class Session {
  constructor(username) {
    this.user = username;
  }
}

const s1 = new Session("Bryce");
const s2 = new Session(); // another different instance

console.log(s1.user); // "Bryce"
console.log(s2.user); // undefined
console.log(s1 === s2); // false

🔴 Problem

If your app creates sessions in different places, you'll have different instances and the state can be inconsistent.

4) Singleton (recommended version): getInstance()

This is the clearest form for a junior because there's no magic in the constructor.

Step 4.1: Create the class with a "saved" instance

We use a private static property to save the unique instance:


class Session {
  static #instance = null; // here we'll save the only instance
  user = null;

  constructor() {
    // normal constructor (no tricks)
  }
}

Step 4.2: Create the global access point getInstance()


class Session {
  static #instance = null;
  user = null;

  constructor() {}

  static getInstance() {
    // If it doesn't exist, we create it
    if (!Session.#instance) {
      Session.#instance = new Session();
    }
    // If it exists, we return the same one
    return Session.#instance;
  }
}

✅ We already have singleton

It will always return the same instance.

5) Add real behavior: login, read user, clear


class Session {
  static #instance = null;
  user = null;

  constructor() {}

  static getInstance() {
    if (!Session.#instance) {
      Session.#instance = new Session();
    }
    return Session.#instance;
  }

  login(username) {
    this.user = username;
  }

  clear() {
    this.user = null;
  }
}

6) Test that it works (the key demo)


const s1 = Session.getInstance();
s1.login("Bryce");

const s2 = Session.getInstance();

console.log(s1.user); // "Bryce"
console.log(s2.user); // "Bryce"
console.log(s1 === s2); // true ✅ same instance

✅ This demonstrates the concept

No matter how many times you access it, it's always the same instance.

7) "Reset" for tests or to completely restart

In tests it's common to want to "start clean". We can add a static method to reset:


class Session {
  static #instance = null;
  user = null;

  constructor() {}

  static getInstance() {
    if (!Session.#instance) {
      Session.#instance = new Session();
    }
    return Session.#instance;
  }

  login(username) {
    this.user = username;
  }

  clear() {
    this.user = null;
  }

  static resetForTests() {
    Session.#instance = null;
  }
}

Usage:


Session.resetForTests();
const s = Session.getInstance();
console.log(s.user); // null

8) Alternative version (classic): "return in the constructor"

This is seen a lot in old examples. It works, but it's more confusing.


class Session {
  static instance = null;

  constructor(username) {
    if (Session.instance) return Session.instance;

    this.user = username;
    Session.instance = this;
  }
}

const s1 = new Session("Bryce");
const s2 = new Session("Other");

console.log(s1.user); // "Bryce"
console.log(s2.user); // "Bryce" (ignores "Other")
console.log(s1 === s2); // true

⚠️ Important

The second time you do new Session("Other"), that parameter is ignored because it returns the previous instance.

9) The most common way in modern JS: Singleton by module

In real projects, you often do this:


// session.js
class Session {
  user = null;
  login(name) { this.user = name; }
  clear() { this.user = null; }
}

export const session = new Session();

✅ Advantage

Since modules are cached, session will be the same object for whoever imports it.

10) When NOT to use Singleton (senior lesson)

Singleton can be a bad idea when:

  • You need easy testing (global state breaks tests)
  • You have multiple concurrent users (backend)
  • You want decoupled code (dependency injection is usually better)

⚠️ Backend warning

In Node/Express, a singleton lives in the process, so do NOT save "current user" globally or you'll mix users.

✅ Summary

What you must remember

  • Singleton = a single instance
  • Ideal for global resources (logger, config, cache)
  • In modern JS: getInstance() or singleton by module
  • Avoid it if it introduces global state that's hard to test or if it's "per user" state

Common Errors Checklist

⚠️ Typical errors to avoid

  • ❌ Using singleton for "per user" state in backend
  • ❌ Not providing a reset method for tests
  • ❌ Overusing the pattern when dependency injection would be better
  • ❌ Not documenting that a class is a singleton
