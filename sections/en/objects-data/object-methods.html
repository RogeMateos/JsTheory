Object Methods (assign, keys, values, entries)

The Real-World Problem

Imagine you work on an analytics site and need to build a payload for an event:


const baseEvent = { event: "select_item", page: "Renewals" };
const userContext = { userId: "u123", loggedIn: true };
const itemContext = { itemId: "car_456", price: 220 };

// How do I combine these 3 objects into one?

Challenge

You need to combine multiple objects into one without modifying the originals.

Solution 1: Spread Operator (The Modern Way) ✅

The most idiomatic and readable way in modern JavaScript:


const baseEvent = { event: "select_item", page: "Renewals" };
const userContext = { userId: "u123", loggedIn: true };
const itemContext = { itemId: "car_456", price: 220 };

const payload = { ...baseEvent, ...userContext, ...itemContext };

console.log(payload);
// {
//   event: "select_item",
//   page: "Renewals",
//   userId: "u123",
//   loggedIn: true,
//   itemId: "car_456",
//   price: 220
// }

✅ Advantages of Spread

  • More readable and modern
  • Most common pattern in React
  • Doesn't modify the original objects

Solution 2: Object.assign() (Legacy Code)

Object.assign() copies properties from one or more source objects to a target object.


const baseEvent = { event: "select_item", page: "Renewals" };
const userContext = { userId: "u123", loggedIn: true };
const itemContext = { itemId: "car_456", price: 220 };

// ✅ Create new object (target = {})
const payload = Object.assign({}, baseEvent, userContext, itemContext);

console.log(payload);
// { event, page, userId, loggedIn, itemId, price }

Mnemonic rule

The first parameter is the one that gets modified (if you don't use {} as target).

⚠️ Pitfall 1: Target Object Mutation

This is the most dangerous trap of Object.assign():


const personCore = { name: "Roge" };
const personDetails = { age: 30, alias: "MoureDev" };

// ❌ MUTATES personCore (target = personCore)
Object.assign(personCore, personDetails);
console.log(personCore);
// { name: "Roge", age: 30, alias: "MoureDev" }
// personCore was modified!

// ✅ Doesn't mutate anything (target = {})
const fullPerson = Object.assign({}, personCore, personDetails);
// Now personCore remains intact

🔥 Why this matters

In real applications, mutating shared objects can break:

  • React (unexpected re-renders)
  • Redux/Zustand (state management)
  • Caches and shared references

✅ Solution

Always use {} as first parameter or better yet, use spread { ...obj }

⚠️ Pitfall 2: Key Conflicts (Last One Wins)

If two objects have the same property, the last source object overwrites:


const a = { name: "Roge", role: "developer" };
const b = { name: "Other", city: "London" };

const result = Object.assign({}, a, b);
console.log(result.name); // "Other" ← b wins
console.log(result);
// { name: "Other", role: "developer", city: "London" }

💡 Golden Rule

👉 If there's a collision, the last parameter wins.

Same behavior with spread


const result = { ...a, ...b };
console.log(result.name); // "Other"

⚠️ Pitfall 3: Shallow Copy

If there are nested objects, they are NOT cloned: the reference is copied.


const core = {
  name: "Roge",
  address: { city: "London" }  // ← nested object
};

const copy = Object.assign({}, core);

// We modify the city in the copy
copy.address.city = "Madrid";

// The original also changed! 🔥
console.log(core.address.city); // "Madrid"

🔥 Why this happens

Both Object.assign() and spread do shallow copy:

  • Primitive properties are copied
  • Nested objects/arrays are copied by reference

✅ Solutions for deep copy

Modern (modern browsers):


const deepCopy = structuredClone(core);
deepCopy.address.city = "Madrid";
console.log(core.address.city); // "London" ✅

Legacy:


// JSON (only works if no functions/Date/undefined)
const deepCopy = JSON.parse(JSON.stringify(core));

// Or use libraries like lodash
import { cloneDeep } from 'lodash';
const deepCopy = cloneDeep(core);

⚠️ Pitfall 4: What Exactly Gets Copied

Object.assign() copies own enumerable properties (including enumerable symbols), and copies values, not descriptors.

Technical rule

It doesn't copy getters/setters as descriptors, it copies the result/value depending on the case.

Object Inspection: keys, values, entries

Now that you have your combined object, how do you inspect it?


const payload = {
  event: "select_item",
  page: "Renewals",
  userId: "u123",
  loggedIn: true,
  itemId: "car_456",
  price: 220
};

// Get only the keys
console.log(Object.keys(payload));
// ["event", "page", "userId", "loggedIn", "itemId", "price"]

// Get only the values
console.log(Object.values(payload));
// ["select_item", "Renewals", "u123", true, "car_456", 220]

// Get [key, value] pairs
console.log(Object.entries(payload));
// [
//   ["event", "select_item"],
//   ["page", "Renewals"],
//   ["userId", "u123"],
//   ["loggedIn", true],
//   ["itemId", "car_456"],
//   ["price", 220]
// ]

Practical Iteration with entries + for...of

The most useful way in the real world:


const payload = {
  event: "select_item",
  page: "Renewals",
  userId: "u123",
  price: 220
};

// ✅ With destructuring (most idiomatic)
for (const [key, value] of Object.entries(payload)) {
  console.log(`${key}:`, value);
}

// Output:
// event: select_item
// page: Renewals
// userId: u123
// price: 220

✅ This is gold for juniors

Instead of using indices [0] and [1], destructure directly as [key, value].

Real use cases


// Convert object to query string
const params = { page: 1, limit: 10, sort: "name" };
const queryString = Object.entries(params)
  .map(([key, value]) => `${key}=${value}`)
  .join('&');
console.log(queryString); // "page=1&limit=10&sort=name"

// Filter properties from an object
const user = { name: "Roge", age: 30, password: "secret123" };
const publicUser = Object.fromEntries(
  Object.entries(user).filter(([key]) => key !== 'password')
);
console.log(publicUser); // { name: "Roge", age: 30 }

Key Ordering (Real Nuance)

The order is usually stable, but it's not simply "the order you wrote it":


const obj = { 2: "b", 1: "a", name: "Roge", age: 30 };

console.log(Object.keys(obj));
// ["1", "2", "name", "age"]
// ↑ Numbers first (ascending order), then strings (insertion order)

📌 Ordering rule

Numeric keys are sorted first in ascending order, then strings in insertion order.

Difference with for...in

Many people confuse Object.keys() with for...in:


const base = { inherited: true };
const obj = Object.create(base);
obj.own = true;

// Object.keys → only own properties
console.log(Object.keys(obj)); // ["own"]

// for...in → also iterates inherited from prototype
for (const k in obj) {
  console.log(k); // "own" and "inherited"
}

✅ Key differences

  • Object.keys(obj) → only own properties
  • for...in → also iterates inherited properties from prototype

If you need to filter in for...in


for (const k in obj) {
  if (obj.hasOwnProperty(k)) {
    console.log(k); // only "own"
  }
}

Summary: When to Use Each One

Combining objects

  • ✅ Spread { ...a, ...b } → modern, readable code
  • ⚠️ Object.assign({}, a, b) → legacy code, less readable

Inspecting objects

  • Object.keys() → get only keys
  • Object.values() → get only values
  • Object.entries() → get [key, value] pairs

Iterating objects

  • ✅ for (const [k, v] of Object.entries(obj)) → modern, with destructuring
  • ⚠️ for...in → includes inherited, needs hasOwnProperty filter

Pitfalls Checklist

⚠️ Common errors to avoid

  • ❌ Mutating the original object with Object.assign(obj, ...)
  • ❌ Assuming Object.assign does deep copy
  • ❌ Not considering key collisions when combining objects
  • ❌ Using for...in without filtering with hasOwnProperty
