Objects and Primitive Values

Objects in JavaScript

An object in JavaScript is a complex data type that allows you to store collections of data and more complex entities. Objects can contain properties and methods.

  • They are mutable (can be changed after creation)
  • They are stored and copied by reference
  • They can contain multiple values as properties
  • They can have methods (functions as properties)

      let person = {
        name: "Alice",
        age: 30,
        greet: function() {
          console.log("Hello, I'm " + this.name);
        }
      };
      
      person.greet(); // Output: Hello, I'm Alice

Primitive Values

Primitive values are the simplest data types in JavaScript. They include:

  • String
  • Number
  • Boolean
  • Undefined
  • Null
  • Symbol
  • BigInt

Key characteristics of primitives:

  • They are immutable (cannot be changed after creation)
  • They are stored and copied by value
  • They represent a single value

      let str = "Hello";
      let num = 42;
      let bool = true;
      let undef = undefined;
      let n = null;
      let sym = Symbol("unique");
      let bigInt = 1234567890123456789012345678901234567890n;

Main Differences

  1. Complexity: Primitives are simple, single values; Objects can contain multiple values and have complex structures.
  2. Mutability: Primitives are immutable; Objects are mutable.
  3. Storage and copying: Primitives are copied by value; Objects are copied by reference.
  4. Comparison: Primitives are compared by value; Objects are compared by reference.
  5. Methods: Primitives don't have methods (although JavaScript temporarily wraps them in objects to allow method-like syntax); Objects can have methods.

      // Primitives
      let a = 5;
      let b = a;
      b = 10;
      console.log(a); // 5
      console.log(b); // 10

      // Objects
      let obj1 = {x: 5};
      let obj2 = obj1;
      obj2.x = 10;
      console.log(obj1.x); // 10
      console.log(obj2.x); // 10

Constructor Functions and prototype (Pre-ES6 Era)

🏭 The Metaphor: Person is a factory

Static methods: are factory tools

  • Used like: Person.createFromJSON(...)
  • Don't depend on a specific person

Instance methods: are abilities that all manufactured persons have

  • Used like: bruce.greet()
  • Depend on this (the concrete object)

A) Constructor (properties per instance)


function Person(name, age) {
  this.name = name;
  this.age = age;
}

B) Instance method (shared) → goes in prototype


Person.prototype.greet = function () {
  return `Hello, I'm ${this.name}`;
};

✅ Why in prototype

Person.prototype.greet → found by instances through the prototype chain

All instances share the same function (memory savings)

C) Static method → goes on the Person function


Person.createAnonymous = function () {
  return new Person("Anonymous", 0);
};

✅ Static method

Person.createAnonymous → belongs to the "factory", not the "products"

D) Usage


const bruce = new Person("Bruce", 30);

console.log(bruce.greet());           // ✅ "Hello, I'm Bruce" (instance method)
console.log(Person.createAnonymous()); // ✅ Person { name: 'Anonymous', age: 0 }

console.log(bruce.createAnonymous);    // ❌ undefined (not an instance method)
console.log(Person.greet);             // ❌ undefined (greet is not static)

⚠️ Common mistake: "I added the method and it doesn't appear"

If you do this:


Person.greet = function () { ... }  // ❌ Static (common error)

Then:


bruce.greet() // ❌ TypeError: bruce.greet is not a function

Solution: Must go in Person.prototype.greet

Simple rule

  • Person.something = static
  • Person.prototype.something = instance

E) prototype vs __proto__ (understanding the connection)


const bruce = new Person("Bruce", 30);

// Verification:
console.log(Object.getPrototypeOf(bruce) === Person.prototype);
// true

📌 Mini-diagram

  • Person.prototype → the object that will be the "parent" (prototype) of instances created with new Person()
  • Object.getPrototypeOf(bruce) → points to Person.prototype

⚠️ Avoid __proto__

__proto__ is considered legacy/compat

Use instead:

  • Object.getPrototypeOf(obj) to get the prototype
  • Object.setPrototypeOf(obj, proto) to set it (with caution, it's slow)

F) Why put methods in prototype (performance/memory)

❌ Define inside the constructor:

function Person(name) {
  this.name = name;
  this.greet = function () {
    return `Hello, I'm ${this.name}`;
  };
}

const a = new Person("A");
const b = new Person("B");

console.log(a.greet === b.greet); // false
// 👉 Each instance creates a new copy of greet (more memory)
✅ Define in prototype:

function Person(name) {
  this.name = name;
}

Person.prototype.greet = function () {
  return `Hello, I'm ${this.name}`;
};

const a = new Person("A");
const b = new Person("B");

console.log(a.greet === b.greet); // true
// 👉 All instances share the same function

💡 This true is the "click" for many juniors

Proves that both objects use the same function in memory.

G) Modern version (class) and equivalencies


class Person {
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }

  greet() { // ✅ instance method (lives in Person.prototype)
    return `Hello, I'm ${this.name}`;
  }

  static createAnonymous() { // ✅ static method (lives in Person)
    return new Person("Anonymous", 0);
  }
}

const bruce = new Person("Bruce", 30);
console.log(bruce.greet());           // "Hello, I'm Bruce"
console.log(Person.createAnonymous()); // Person { name: 'Anonymous', age: 0 }

📌 Real equivalencies

  • greet() in class → goes to prototype
  • static createAnonymous() → goes to constructor/class

class is syntactic sugar over the same prototype system

⚠️ Important: NOT deprecated

Constructor functions and prototype are NOT deprecated

  • Today class is preferred for readability and standard
  • But prototype is still the real engine underneath
  • In legacy projects you'll see constructor functions constantly

H) Practical exercises

1️⃣ Create Person.fromObject({name, age}) as a static method


// Your code here
Person.fromObject = function(obj) {
  return new Person(obj.name, obj.age);
};

// Test:
const p = Person.fromObject({name: "Ana", age: 25});
console.log(p.greet()); // "Hello, I'm Ana"

2️⃣ Add isAdult() as an instance method


// Your code here
Person.prototype.isAdult = function() {
  return this.age >= 18;
};

// Test:
const minor = new Person("Luis", 15);
const adult = new Person("Ana", 25);
console.log(minor.isAdult()); // false
console.log(adult.isAdult()); // true

3️⃣ Demonstrate that the instance method is shared


const a = new Person("A", 20);
const b = new Person("B", 30);

console.log(a.greet === b.greet); // true (if in prototype)
console.log(a.isAdult === b.isAdult); // true

I) Mental checklist (3 golden rules)

  • ✅ Unique properties per instance → inside the constructor
  • ✅ Shared methods → in prototype
  • ✅ "Factory" methods/properties → static (on the function/class)

Classes in JavaScript (ES6+)

Step 1 — The Real Problem

Imagine you need to create multiple persons with the same properties and methods:


// ❌ With object literals, you repeat logic
const p1 = {
  name: "Bryce",
  age: 37,
  greet() {
    return `Hello, I'm ${this.name}`;
  }
};

const p2 = {
  name: "Ana",
  age: 22,
  greet() {
    return `Hello, I'm ${this.name}`;
  }
};

// Problem: you're duplicating the greet method

The pain of object literals

  • Works for one object
  • If you need many persons with same properties and methods, you repeat logic
  • Hard to maintain when you change behavior

Step 2 — Old Solution: Constructor Function + prototype

Here's where we came from and why prototype exists:


function Person(name, age) {
  this.name = name;
  this.age = age;
}

Person.prototype.greet = function () {
  return `Hello, I'm ${this.name}`;
};

const person = new Person("Bryce", 37);
console.log(person.greet()); // "Hello, I'm Bryce"

Key point

greet is in Person.prototype, not duplicated per instance.

This saves memory when you have 1000 persons.

Step 3 — Modern Solution: class (Same Idea, More Readable)

ES6 introduced class syntax, which is syntactic sugar over prototypes:


class Person {
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }

  greet() {
    return `Hello, I'm ${this.name}`;
  }
}

const person = new Person("Bryce", 37);
console.log(person.greet()); // "Hello, I'm Bryce"

✅ Important phrase

Person.prototype.greet still exists.

The class syntax is just a clearer way to write the same prototype pattern.

Step 4 — Demonstration: class == prototype Underneath

Eye-opening example:


class Person {
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }

  greet() {
    return `Hello, I'm ${this.name}`;
  }
}

// Revealing the truth:
console.log(typeof Person); // "function" ← it's a function!
console.log(Person.prototype.hasOwnProperty("greet")); // true

const person = new Person("Bryce", 37);
console.log(Object.getPrototypeOf(person) === Person.prototype); // true

💡 Explanation

"A class in JS is a special function, and its methods go to the prototype."

It's not like Java or C#. JavaScript is still prototypal.

Step 5 — Getters/Setters with a Real Case

I'm not mentioning this "just to mention it". Let's see a business case: prevent negative ages.


class Person {
  constructor(name, age) {
    this.name = name;
    this.age = age; // will trigger the setter
  }

  get age() {
    return this._age;
  }

  set age(value) {
    if (value < 0) {
      throw new Error("Age cannot be negative");
    }
    this._age = value;
  }

  greet() {
    return `Hello, I'm ${this.name}`;
  }
}

const person = new Person("Bryce", 37);
console.log(person.age); // 37 (uses the getter)

person.age = 40; // uses the setter
console.log(person.age); // 40

person.age = -5; // Error: Age cannot be negative

✅ Senior tip

  • Use _age as backing field (convention for "private")
  • Explain that age "looks like a property" but is a method
  • Getters/setters allow validation without changing the external API

Step 6 — Privacy: What Actually Works Today

There are 2 most common ways for private fields:

1) Real private fields (modern) #

class Person {
  #ssn; // real private

  constructor(name, age, ssn) {
    this.name = name;
    this.age = age;
    this.#ssn = ssn;
  }

  getSSNMasked() {
    return "****-" + this.#ssn.slice(-4);
  }
}

const person = new Person("Bryce", 37, "123-45-6789");
console.log(person.getSSNMasked()); // "****-6789"
console.log(person.#ssn); // SyntaxError: Private field '#ssn'

✅ Advantages of #privateField

  • Real privacy, not convention
  • Runtime error if you try to access from outside
  • Support in modern browsers (2022+)
2) Underscore convention (semi-private)

class Person {
  constructor(name, age) {
    this.name = name;
    this._age = age; // convention: "don't touch this"
  }

  get age() {
    return this._age;
  }
}

const person = new Person("Bryce", 37);
console.log(person._age); // 37 (accessible, but "you shouldn't")

⚠️ Important

The _underscore is just convention, NOT truly private.

Anyone can access person._age.

Key Difference: Method in Class vs Function in Constructor

Many juniors make this mistake:

❌ This duplicates function per instance (BAD)

class Person {
  constructor(name) {
    this.name = name;
    this.greet = () => `Hello ${this.name}`; // ❌ copy per instance
  }
}

const a = new Person("A");
const b = new Person("B");

console.log(a.greet === b.greet); // false ← each instance has its copy
✅ This shares method (GOOD)

class Person {
  constructor(name) {
    this.name = name;
  }

  greet() {
    return `Hello ${this.name}`; // ✅ in prototype, shared
  }
}

const a = new Person("A");
const b = new Person("B");

console.log(a.greet === b.greet); // true ← both use the same function

💡 Why it matters (memory/performance)

If you create 1000 instances:

  • ❌ Bad version: 1000 copies of greet in memory
  • ✅ Good version: 1 single copy of greet in Person.prototype

instanceof and Prototype Chain

Very useful for understanding instances:


class Person {
  constructor(name) {
    this.name = name;
  }
}

const person = new Person("Bryce");

console.log(person instanceof Person); // true
console.log(person instanceof Object); // true
console.log(person instanceof Array);  // false

// Verify the prototype chain
console.log(Object.getPrototypeOf(person) === Person.prototype); // true
console.log(Object.getPrototypeOf(Person.prototype) === Object.prototype); // true

Complete chain

person → Person.prototype → Object.prototype → null

When NOT to Use Classes (Real Modern JS)

In current React/Frontend:

✅ Reality of modern development

  • Many times you use pure functions + objects
  • Classes exist, but you don't model everything as "entities"
  • React Hooks uses functions, not classes (since 2019)
  • Functional programming is more trendy than classic OOP
Example: modern functional style

// Instead of a Person class, you could use:
const createPerson = (name, age) => ({
  name,
  age,
  greet: () => `Hello, I'm ${name}`
});

const person = createPerson("Bryce", 37);
console.log(person.greet()); // "Hello, I'm Bryce"

⚠️ When to YES use classes

  • When you model "entities" with mutable state
  • When you need inheritance (extends)
  • When working with libraries that use them (some frameworks)
  • When the team prefers OOP style

Mini Summary (Senior Style)

The truth about classes in JavaScript

  • "Before, we created instances with constructor functions and prototypes."
  • "Today we use class, which is more readable, but still uses prototypes underneath."
  • "constructor initializes state with this."
  • "Methods in class are saved in Person.prototype, so they're shared."
  • "You can add methods to prototype after, but in real apps we try to avoid it."
  • "Getters/setters are for validating or controlling access as if it were a property."
  • "Modern privacy: #privateField."

Inheritance Through Prototypes (Object.create)

🧬 STEP 1: What "inherit" means in JavaScript

In JavaScript, inherit does NOT mean copying properties.

It means pointing to another object to reuse it.

⚠️ This is key

Data is not copied, it's shared through the prototype.

🧩 STEP 2: Base object (person)


const person = {
  name: "Bryce",
  age: 37,
  greet() {
    console.log(`Hello, I'm ${this.name}`);
  },
  sayAge() {
    console.log(`I'm ${this.age} years old`);
  }
};

📌 So far:

  • A normal object
  • Properties + methods
  • No inheritance yet

🧬 STEP 3: Create an object that inherits (Object.create)


const programmer = Object.create(person);

👉 Important

This does NOT copy person

This creates an empty object whose prototype is person

Visually:


programmer
   ↓ prototype
person

🔍 STEP 4: Why does it look "empty"?


console.log(programmer); // {}

⚠️ This is very confusing

The object is empty, but has access to the prototype's properties.

Let's try:


programmer.greet();   // Hello, I'm Bryce
programmer.sayAge(); // I'm 37 years old

✔️ It works

Because JS searches in the prototype chain

🔗 STEP 5: How the lookup works (prototype chain)

When you do:


programmer.name

JavaScript does this:

  1. Does name exist in programmer? ❌
  2. Does it exist in its prototype (person)? ✅
  3. → Use that value

💡 THE HEART of the prototype system

This chain lookup is the foundation of inheritance in JavaScript.

⚠️ STEP 6: The famous undefined (surgical precision here)

If you do:


console.log(programmer.greet());

You get:


Hello, I'm Bryce
undefined

Why?

  • greet() does console.log
  • But returns nothing
  • Any function that doesn't return → undefined

💡 Important for juniors:

This is NOT an inheritance problem

This is how functions work in JavaScript

🧪 STEP 7: Add properties to the child


programmer.language = "JavaScript";

Now:


console.log(programmer.language); // JavaScript
console.log(person.language);     // undefined

👉 New properties DON'T go up to the prototype

Each object maintains its own properties separately.

🔄 STEP 8: What happens if I modify the prototype


person.name = "MoureDev";
programmer.greet(); // Hello, I'm MoureDev

Why?

  • programmer does NOT have name
  • Still uses the one from the prototype
  • Change the prototype → changes the result

⚠️ This is powerful but dangerous

🧠 STEP 9: But… is this "real" inheritance?

Important reflection

This is NOT classical inheritance.

It's delegation through prototypes.

That's why:

  • There's no copying
  • There's dependency
  • Changing the parent affects the children

🏁 STEP 10: Modern conclusion (very important)

💡 Key message

  • Before ES6, this was the only way to "inherit"
  • Today we use class, which underneath still uses prototypes

Understanding prototypes makes you a better developer, even if you use classes every day.

Complete example


// Base
const person = {
  name: "Bryce",
  age: 37,
  greet() {
    return `Hello, I'm ${this.name}`;
  }
};

// Inheritance
const programmer = Object.create(person);
programmer.language = "JavaScript";

// Functionality
console.log(programmer.greet());    // "Hello, I'm Bryce"
console.log(programmer.language);   // "JavaScript"

// Verify
console.log(programmer.hasOwnProperty("language")); // true
console.log(programmer.hasOwnProperty("name"));     // false
console.log(Object.getPrototypeOf(programmer) === person); // true
