Callbacks in JavaScript

What is a Callback?

A callback is a function passed as an argument to another function, to be executed later (usually when something finishes).

It's like saying: "When you're ready, call THIS function".

Simple Example (without asynchrony)


function processData(data, callback) {
  callback(data);
}

processData("Hello", (message) => {
  console.log("Message:", message);
});
// Output: Message: Hello

What's happening here?

  1. You call processData("Hello", ...)
  2. callback is the function you passed
  3. Inside it executes: callback(data)
  4. Prints: Message: Hello

💡 See detailed explanation on ChatGPT

Synchronous vs Asynchronous Code

Synchronous Code (blocks the thread)

Code executes line by line, and each line "finishes" before moving to the next.


console.log("A");
console.log("B");
console.log("C");

// Output:
// A
// B
// C

Asynchronous Code (doesn't block)

There are operations that JavaScript doesn't execute right away, instead it says: "I'll do this later, when I can".

Typical examples:

  • Timers (setTimeout)
  • Network requests (fetch)
  • Events (click)
  • File reading (Node.js)

First Contact with Asynchrony: setTimeout

setTimeout receives:

  • Callback function (what you want to execute)
  • Time in ms (when)

setTimeout(() => {
  console.log("This executes later");
}, 2000);

The Key Example: Why does it output "Start, End, This..."?


console.log("Start");

setTimeout(() => {
  console.log("This executes");
}, 0);

console.log("End");

Actual output:

Start
End
This executes

Important Correction

This is NOT "synchronous" execution.
setTimeout is always asynchronous (even with 0).

The Engine Parts: Call Stack, Web APIs, Task Queue, Event Loop

1. Call Stack

  • Where synchronous code executes
  • It's a stack: last in, first out

2. Web APIs

The browser (or Node) offers "external tools" like:

  • setTimeout
  • fetch
  • DOM events

JavaScript says: "Hey browser, you handle the timer".

3. Task Queue (MacroTasks)

When the timer finishes, its callback doesn't execute directly.
It goes into a queue waiting its turn.

4. Event Loop

It's like the "traffic controller":

  • Checks if the Call Stack is empty
  • If it is, takes a task from the queue and puts it in the Call Stack

Step by Step of the "Start / End / This..." Example


console.log("Start");

setTimeout(() => {
  console.log("This executes");
}, 0);

console.log("End");

Step 1

console.log("Start") enters Call Stack → executes → leaves

Prints: Start

Step 2

setTimeout(...) enters Call Stack → registers timer in Web APIs → leaves

⚠️ The callback does NOT execute here.

Step 3

console.log("End") enters Call Stack → executes → leaves

Prints: End

Step 4

Now the Call Stack is empty.
The timer has finished (0ms) → its callback is in Task Queue.
Event Loop puts it in the Call Stack.

Executes: This executes

✅ That's why it comes last.

setTimeout with Real Time (2 seconds)


console.log("Start");

setTimeout(() => {
  console.log("This executes after 2s");
}, 2000);

console.log("End");

Output:

Start
End
(waits 2s)
This executes after 2s

Chaining Asynchronous Tasks with Callbacks

Let's create three asynchronous functions:


function stepOne(callback) {
  setTimeout(() => {
    console.log("Step 1 completed");
    callback();
  }, 1000);
}

function stepTwo(callback) {
  setTimeout(() => {
    console.log("Step 2 completed");
    callback();
  }, 1000);
}

function stepThree(callback) {
  setTimeout(() => {
    console.log("Step 3 completed");
    callback();
  }, 1000);
}

Case A: Launch them "in parallel" (independent)


stepOne(() => console.log("stepOne finishes"));
stepTwo(() => console.log("stepTwo finishes"));
stepThree(() => console.log("stepThree finishes"));

These may finish in different order depending on each one's timing.

Case B: Dependent (1 → 2 → 3)

Here the typical pattern emerges:


stepOne(() => {
  stepTwo(() => {
    stepThree(() => {
      console.log("All steps completed");
    });
  });
});

Output (approx):

Step 1 completed
Step 2 completed
Step 3 completed
All steps completed

Result

✅ Works perfectly.
❌ But the code starts to "go to the right" (nesting).

Callback Hell: What It Is and Why It Happens

Definition

Callback Hell occurs when:

  • You have multiple asynchronous tasks
  • Each depends on the previous one
  • And you chain them with nested callbacks

Result:

  • Code difficult to read
  • Difficult to maintain
  • Difficult to debug
  • Difficult to handle errors

Example "hell" (more realistic):


login(user, () => {
  getProfile(() => {
    getOrders(() => {
      processPayment(() => {
        console.log("all done");
      });
    });
  });
});

It's not impossible:
it's just a nightmare for humans.

Why This Pushes Towards Promises

To solve the chaos:

  • Promises were born
  • And then came async/await

How it would look with promises (just a preview):


stepOnePromise()
  .then(stepTwoPromise)
  .then(stepThreePromise)
  .then(() => console.log("All steps completed"));

💡 And with async/await it's even more readable (you'll see this in the next chapter).

Final Summary

Key Concepts

  • Callback: function passed to another function to execute later
  • setTimeout is always asynchronous, even with 0
  • Call Stack executes synchronous code
  • Web APIs handle timers/network/events
  • Task Queue stores ready callbacks
  • Event Loop puts tasks in the stack when it's empty
  • Callback Hell = too much nesting from dependencies

Interview Question

Why doesn't setTimeout(..., 0) execute "instantly"?

Because setTimeout is always asynchronous. The callback is registered in Web APIs, then goes to the Task Queue, and the Event Loop only executes it when the Call Stack is empty.
