Consuming an API in JavaScript with fetch

Step-by-step guide

1. Why do we need to consume APIs?

In real applications (web, mobile, dashboards, etc.) we almost never work only with local data.
We normally need:

  • Data from a server
  • User information
  • Lists (posts, products, orders…)
  • Save or update information

All of this is done by communicating with APIs using the HTTP protocol.

2. The key problem: asynchrony

When an application makes a request to a server:

  • ❌ We don't want to block the app
  • ❌ We don't want the interface to "freeze"
  • ✅ We want the app to keep working while data arrives

That's why network requests in JavaScript are asynchronous.

JavaScript launches the request, continues executing code and receives the result later.

3. The native tool: fetch

JavaScript natively offers the fetch function to make HTTP requests.

Key ideas:

  • fetch initiates a network request
  • Returns a Promise
  • Doesn't block the main thread
  • Works in modern browsers (and in Node with support)

Mental model:

"I request something now and promise to handle the response when it arrives".

4. Test API: JSONPlaceholder

To learn we don't need to create a backend.
We're going to use a free public API:

JSONPlaceholder
An API with fake data for practice.

It has endpoints like:

  • /posts
  • /users
  • /comments
  • /albums

Example URL:

https://jsonplaceholder.typicode.com/posts

If you access from the browser you'll see:

  • A JSON
  • A list of objects
  • Structured data with key–value

This is exactly what frontend applications consume.

5. First GET request with fetch

Let's make a GET request to get all posts.

fetch("https://jsonplaceholder.typicode.com/posts")
  .then(response => {
    console.log(response);
  });

What is response?

⚠️ Important point that many juniors don't understand at first.

response is NOT the data yet.

It's an object that contains:

  • HTTP code (status)
  • Headers
  • Request information
  • The body (body), still unprocessed

6. Converting the response to JSON

Since we know (from the documentation) that the API returns JSON, we must transform the response.

fetch("https://jsonplaceholder.typicode.com/posts")
  .then(response => {
    return response.json();
  })
  .then(data => {
    console.log(data);
  });

What's happening here

  • fetch → makes the request
  • First then → converts the body to JSON
  • Second then → we now have the ready data
  • data → is an array of posts

7. Why does response.json() return a Promise?

Because:

  • Reading the body is an asynchronous process
  • It can fail (invalid JSON, empty body, etc.)

Mental rule:

Each asynchronous step returns a Promise.

8. Error handling (very important)

Common error

Many believe that:

"If the server responds 404 or 500, it goes into catch".

❌ That's not true.

fetch only goes into catch if:

  • There's a network error
  • Connection problem
  • CORS blocked
  • The request is cancelled

HTTP errors do NOT automatically throw an error.

9. Correct way to handle HTTP errors

We must check response.ok.

fetch("https://jsonplaceholder.typicode.com/posts")
  .then(response => {
    if (!response.ok) {
      throw new Error(`HTTP error ${response.status}`);
    }
    return response.json();
  })
  .then(data => {
    console.log("Data:", data);
  })
  .catch(error => {
    console.error("Error:", error);
  });

What we achieve with this

  • We convert HTTP errors into real errors
  • The catch now does capture important failures
  • More professional and predictable code

10. Recommended version today: async / await

For most people, this form is more readable and clear.

async function getPosts() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/posts");

    if (!response.ok) {
      throw new Error(`HTTP error ${response.status}`);
    }

    const data = await response.json();
    console.log(data);
    return data;

  } catch (error) {
    console.error("Error:", error);
  }
}

getPosts();

Advantages of async/await

  • More linear code
  • Easier to read
  • Easier to debug
  • Ideal for real projects and React

11. POST requests (create data)

So far we've only read data.
Let's send information to the server.

async function createPost() {
  const response = await fetch(
    "https://jsonplaceholder.typicode.com/posts",
    {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        title: "My first post",
        body: "Post content",
        userId: 1,
      }),
    }
  );

  const data = await response.json();
  console.log(data);
}

createPost();

Important details

  • method: HTTP request type
  • headers: describe data format
  • body: always string (usually JSON)

12. Cancelling requests (real case in applications)

Typical example:

  • User changes page
  • User types fast in a search bar
  • We no longer need the previous response
const controller = new AbortController();

fetch("https://jsonplaceholder.typicode.com/posts", {
  signal: controller.signal,
})
  .then(response => response.json())
  .then(data => console.log(data))
  .catch(error => {
    if (error.name === "AbortError") {
      console.log("Request cancelled");
    }
  });

// Cancel the request
controller.abort();

This is very common in modern interfaces.

13. Final best practices

  • ✔️ Always use the API documentation
  • ✔️ Check response.ok
  • ✔️ Handle errors correctly
  • ✔️ Use async/await when possible
  • ✔️ Look at the Network tab in DevTools
  • ✔️ Don't assume the data structure

14. Final mental summary

When you consume an API with fetch:

  1. You make the request
  2. You receive a response
  3. You validate the HTTP status
  4. You transform the data (JSON)
  5. You process the information
  6. You handle errors

If you understand this flow, you understand 80% of API consumption in frontend.
