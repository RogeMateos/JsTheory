Tools for consuming APIs

When we develop an application, we don't always want to test the API from code.
During development, testing or initial API exploration, it's much more convenient to use visual HTTP clients.

These tools allow us to:

  • Test endpoints quickly
  • Send requests without writing JavaScript
  • See server responses in real time
  • Validate that an API works correctly before integrating it into the frontend

🎯 What is a visual HTTP client?

An HTTP client is a tool that allows us to:

  • Send HTTP requests (GET, POST, PUT, DELETE, etc.)
  • Specify the endpoint URL
  • Add parameters, headers and body
  • Analyze the server response (data, time, size, status)

All this without writing code, using a graphical interface.

🧰 Most used tools

🔹 Postman

Postman is one of the most popular tools for working with APIs.

With Postman you can:

  • Choose the HTTP method (GET, POST, PUT, etc.)
  • Enter the API URL
  • Send parameters and headers
  • See the complete result of the request
  • Know if the operation was created correctly or not

It's ideal for:

  • Manual testing
  • Learning how an API responds
  • Testing different scenarios quickly

🔹 APIDog

APIDog stands out especially for its focus on documentation.

It allows:

  • Testing requests like Postman
  • Importing API specifications (OpenAPI / Swagger)
  • Having live documentation connected to real endpoints

This is very common in professional teams:

"I give you the documentation + the specification so you can test the API directly in your tool."

🔹 Thunder Client

Thunder Client is an extension that integrates directly into Visual Studio Code.

Advantages:

  • You don't need to leave the editor
  • Works as a lightweight HTTP client
  • Ideal for frontend developers

From Thunder Client you can:

  • Create a new request
  • Choose HTTP method
  • Add headers (like Content-Type)
  • Send data in JSON format
  • See the response immediately

📥 Mental flow example (without code)

  1. You select an API URL
  2. You make a GET
  3. The server responds with 200 OK
  4. You see the JSON response
  5. You switch to POST
  6. You send a JSON in the body
  7. The server responds with 201 Created
  8. You try an incorrect URL
  9. The server responds with 404 Not Found

This allows you to understand the real behavior of the API before using fetch or axios.

📊 Interpreting server responses

When using these tools, it's key to look at the HTTP status codes:

  • 200 OK → The request went well
  • 201 Created → A new resource was created
  • 404 Not Found → The endpoint doesn't exist
  • 400 / 500 → Client or server errors

This helps you validate:

  • If the API does what it promises
  • If you're sending the data correctly
  • If the endpoint actually exists

✅ Why you should always use them

  • ✔️ They speed up development
  • ✔️ They avoid unnecessary errors in code
  • ✔️ They facilitate debugging
  • ✔️ They're standard in professional teams

👉 Recommendation

Use these tools before writing code and during development to check changes.
