Correct error handling with fetch in JavaScript

When we start consuming APIs with fetch, there's a key detail that's often confusing:

A 404 or 500 does NOT automatically make fetch enter the catch.

Let's understand why this happens, what an error in fetch really means, and how to handle it properly in real applications.

1. The real problem (what usually surprises)

Imagine you call a URL that doesn't exist:

fetch("https://api.example.com/pats")
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => console.error("Error:", err));

You expect it to enter the catch…
but it doesn't, even though the server responds with 404.

❓ Why?

2. How fetch really works

fetch only rejects the promise when a technical network error occurs, for example:

  • No internet connection
  • Incorrect DNS
  • Server unreachable
  • CORS blocked by the browser

But if the server responds, even with:

  • 404 Not Found
  • 401 Unauthorized
  • 500 Internal Server Error

👉 For fetch, that's a valid response.

That's why:

  • ❌ 404 is not an error for fetch
  • ✅ It's an HTTP response with a code you must evaluate

3. Inspecting the response

When fetch responds, you have very useful information:

const response = await fetch(url);

console.log(response.status); // 200, 404, 500...
console.log(response.ok);     // true if 200–299

response.ok

  • true → code between 200 and 299
  • false → any other code (404, 401, 500…)

👉 This property exists precisely to handle HTTP errors.

4. The correct solution: convert HTTP errors into real errors

If a code is not valid for your application, throw an error yourself.

const response = await fetch(url);

if (!response.ok) {
  throw new Error(`HTTP Error ${response.status}`);
}

const data = await response.json();
return data;

What do we gain?

  • Clean flow when everything goes well
  • We centralize errors in the catch
  • Total control over what we consider an "error"

5. Complete example with try / catch

async function getPosts() {
  try {
    const response = await fetch("https://api.example.com/posts");

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const data = await response.json();
    console.log("Data:", data);

  } catch (error) {
    console.error("Something went wrong:", error.message);
  }
}

👉 Now yes:

  • 404 → enters catch
  • 500 → enters catch
  • Network error → enters catch

6. More professional version (senior pattern)

In real projects, it's convenient to create a reusable helper.

async function fetchJson(url, options = {}) {
  const response = await fetch(url, options);

  let body = null;
  const contentType = response.headers.get("content-type") || "";

  if (contentType.includes("application/json")) {
    try {
      body = await response.json();
    } catch {}
  } else {
    try {
      body = await response.text();
    } catch {}
  }

  if (!response.ok) {
    const error = new Error(`Request failed: ${response.status}`);
    error.status = response.status;
    error.url = response.url;
    error.body = body;
    throw error;
  }

  return body;
}

Why is it better?

  • Preserves error information
  • Works for all APIs
  • Facilitates clear messages in the UI

7. Error handling in the interface

try {
  const posts = await fetchJson("/posts");
  render(posts);
} catch (e) {
  if (e.status === 404) showMessage("Resource not found");
  else if (e.status === 401) showMessage("Unauthorized");
  else if (e.status >= 500) showMessage("Server error");
  else showMessage("Unexpected error");
}

👉 Not all errors are shown the same to the user.

8. Important cases you should know

204 No Content

  • Valid response
  • ❌ Don't call response.json() (there's no body)

Invalid JSON

  • Some APIs return HTML in errors
  • Always protect the body reading

CORS

  • The browser can block the response
  • Looks like a network error, even though the server does respond

9. Key summary (to remember)

fetch only fails if the network fails.
HTTP errors (404, 500…) are valid responses and you must handle them yourself with response.ok.
