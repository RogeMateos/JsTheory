Authentication in REST APIs: API Key, Bearer Token and JWT

Step-by-step tutorial

Objective

Understand how many modern APIs authenticate and how to send credentials correctly from JavaScript (fetch), avoiding common errors and security holes.

1) First: Authentication vs Authorization (mental foundation)

Before talking about keys and tokens, remember this:

  • Authentication (AuthN): Who are you?
  • Authorization (AuthZ): What can you do?

Quick example:

  • You log in → authentication ✅
  • You try to view /admin → authorization ✅/❌ depending on role

2) Why does an API need authentication?

Because the API must be able to:

  • Protect resources (private data)
  • Apply permissions (roles/scopes)
  • Limit abuse (rate limiting)
  • Identify the client or user

Without authentication, anyone could call sensitive endpoints.

3) API Key: what it is and when to use it

What it is

An API Key is a text string that identifies a client (app/project).

Example (fictitious):

X-API-Key: 123abc...

When it makes sense

✅ Useful for:

  • Public APIs with quotas
  • Identifying the application (not necessarily end user)
  • Server-to-server (backend to backend)

Typical risk

❌ If you put it in the frontend, it can be copied (DevTools, network, etc.).
So an API Key in the frontend can't be a "real secret", only quota/usage control.

4) Where to send credentials? (important)

Never in the URL

Avoid things like:

https://api.com/data?apiKey=MY_KEY

Because the URL easily leaks in:

  • Browser history
  • Logs
  • Analytics
  • Proxies
  • Referer headers

The correct way: headers (or cookies)

The standard practice is to use headers for tokens:

Authorization: Bearer <token>

5) Token: what it is in real life

A token is usually a string that represents a session/user or permission.

There are two main types:

  • Opaque token: you don't "understand" it, the server does.
  • JWT: token with structure (you can see it and it has claims).

In both cases, it's normal to send it in the Authorization header using Bearer.

Note: it's not "beer token", it's Bearer token.

6) Bearer Token: the practical standard

"Bearer" means:

If you present this token, I treat you as the associated user/client.

HTTP Example:

Authorization: Bearer eyJhbGciOi...

7) JWT: what it is and what it is NOT

What it means

JWT = JSON Web Token

Usually has 3 parts separated by dots:

header.payload.signature

Example:

xxxxx.yyyyy.zzzzz

JWT is normally signed, not encrypted

This is where many people get confused:

  • ✅ Signed (signature): prevents tampering without the server noticing.
  • ❌ Not encrypted by default: the payload can be read (base64).

Golden rule:

Don't put secrets in the JWT payload.

Why JWT is used

Because you can include useful data (claims), such as:

  • user id
  • roles/scopes
  • expiration exp

And the server can validate the signature without always going to the database (depending on architecture).

8) Example: consuming an API with Bearer token (fetch)

Imagine you already have a token (from login or OAuth). You call a protected endpoint:

const token = getAccessToken(); // ideally from memory
const res = await fetch("https://api.myapp.com/profile", {
  headers: {
    Authorization: `Bearer ${token}`,
  },
});

if (!res.ok) throw new Error("Unauthorized or error");
const data = await res.json();
console.log(data);

9) Complete typical flow (the real authentication cycle)

Step A: Login

  1. User enters credentials
  2. Backend validates
  3. Backend returns an access token (and sometimes refresh token)

Step B: Protected requests

On each request:

  1. The frontend sends Authorization: Bearer <accessToken>
  2. The backend validates the token
  3. Responds 200 if ok, 401 if not

Step C: Token expired

If it expires:

  1. Request a new one with refresh token
  2. Retry the request

10) Access token vs Refresh token (very common in modern systems)

Access token

  • Short-lived (minutes)
  • Always sent in Authorization

Refresh token

  • Longer-lived (days/weeks)
  • Used to request new access tokens
  • Usually stored in HttpOnly cookie (more secure)

Advantage:

If the access token is stolen, the damage is time-limited.

11) Basic 401 handling (expiration) in fetch

Simple version: if 401, try to refresh and retry.

async function fetchWithAuth(url, options = {}) {
  const token = getAccessToken();

  let res = await fetch(url, {
    ...options,
    headers: {
      ...(options.headers || {}),
      Authorization: `Bearer ${token}`,
    },
  });

  if (res.status !== 401) return res;

  // 401 -> token expired or invalid
  const refreshed = await refreshAccessToken();
  if (!refreshed) throw new Error("Session expired. Please log in again.");

  const newToken = getAccessToken();
  return fetch(url, {
    ...options,
    headers: {
      ...(options.headers || {}),
      Authorization: `Bearer ${newToken}`,
    },
  });
}

refreshAccessToken() normally calls /auth/refresh and the refresh token goes in HttpOnly cookie.

12) Where to store tokens (practical decision)

This makes the difference between "works" and "is secure".

Recommended option (common pattern)

  • Access token in memory (not localStorage)
  • Refresh token in HttpOnly + Secure cookie

✅ Reduces theft by XSS
⚠️ Requires well-designed refresh endpoint

Simple option (but more dangerous)

  • Access token in localStorage

✅ Easy
❌ If there's XSS, they steal it

13) Best practices checklist (senior level)

  • ✅ Always HTTPS
  • ✅ Never tokens in URL
  • ✅ Access token with short expiration
  • ✅ Refresh token with rotation and revocation
  • ✅ Don't store secrets in JWT payload
  • ✅ Clear scopes/roles
  • ✅ Rate limiting on backend
  • ✅ Logs without exposing tokens
  • ✅ Handle 401/403 properly:
    • 401: not authenticated / invalid token
    • 403: authenticated but without permissions

14) Final summary

  • API Key: identifies the app (not ideal for end user; in frontend it's not secret).
  • Bearer token: standard way to send tokens in Authorization.
  • JWT: token with claims, normally signed (not encrypted), useful for distributed auth.
  • The right way: tokens in headers (or cookies), never in URL.
  • Professional: short access token + refresh token to renew.
