HTTP and Methods (GET, POST, PUT, PATCH, DELETE) for APIs

1) What is HTTP (request/response mental model)

HTTP is the "language" that client (browser/app) and server use to communicate.

  • The client sends a request.
  • The server returns a response.

Mental example:

Request

  • Method: GET
  • URL: /users/42
  • Headers: Accept: application/json

Response

  • Status: 200 OK
  • Headers: Content-Type: application/json
  • Body: { "id": 42, "name": "Roge" }

📌 Key idea: HTTP is not "just for websites", it's for any client-server communication.

2) URL: path and query params (what you "request" and how you filter)

A URL usually has:

  • Path: the resource you want (/users, /users/42)
  • Query params: filters/pagination (?role=admin&page=2)

Examples:

  • GET /users → "give me all users"
  • GET /users/42 → "give me user 42"
  • GET /users?role=admin&page=2 → "give me admins, page 2"

📌 Practical rule: query params are often used in GET to search/filter without sending a body.

3) Parts of a request (what travels from client to server)

A request usually includes:

a) Method

Defines the intention:

  • GET → read
  • POST → create/action
  • PUT → replace
  • PATCH → partially modify
  • DELETE → remove

b) Headers (metadata)

The most typical:

  • Accept: what format you expect to receive (eg: JSON)
  • Content-Type: what format you send (eg: JSON)
  • Authorization: token/cookies (if applicable)

c) Body (content)

Only in methods that send data (POST/PUT/PATCH).
In GET, a body is normally not sent.

4) Parts of a response (what comes back from the server)

A response brings:

a) Status code (most important)

Tells you if it went well or what failed.

b) Headers

Eg: Content-Type: application/json

c) Body

Can be JSON, HTML or empty (for example in 204).

5) HTTP Methods (with real examples)

We'll use a typical resource: users

Common REST convention:

  • Collection: /users
  • Element: /users/:id

5.1 GET (read data)

Used to get information.
Should not change anything on the server.

Examples:

  • GET /users (list)
  • GET /users/42 (detail)
  • GET /users?role=admin&page=2 (filter/pagination)

Example with fetch:

const res = await fetch('/api/users?role=admin&page=2', {
  headers: { Accept: 'application/json' }
});

if (!res.ok) throw new Error('Error loading users');

const users = await res.json();
console.log(users);

5.2 POST (create resource or execute an action)

Used for:

  • Create a new resource in a collection: POST /users
  • Or execute non-idempotent actions: POST /login, POST /payments

Example: create user

const res = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Ana', email: 'ana@mail.com' })
});

if (res.status === 201) {
  const createdUser = await res.json();
  console.log('Created:', createdUser);
} else {
  const error = await res.json().catch(() => null);
  throw new Error(error?.message ?? 'Could not create');
}

📌 Senior note: if you create, typically 201 Created.

5.3 PUT vs PATCH (the difference that prevents most bugs)

PUT = complete replacement (conceptually)

"I send you the entire resource and you leave it like that".

PUT /users/42

await fetch('/api/users/42', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    id: 42,
    name: 'Roge',
    email: 'roge@mail.com',
    role: 'admin'
  })
});

✅ Useful when your UI edits "the complete form".

PATCH = partial update (very common in frontend)

"I send you only what changes".

PATCH /users/42

await fetch('/api/users/42', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ role: 'admin' })
});

📌 Practical rule:

  • If you send everything: PUT
  • If you send only what changed: PATCH

5.4 DELETE (remove)

DELETE /users/42

const res = await fetch('/api/users/42', { method: 'DELETE' });

if (res.status === 204) {
  console.log('Deleted');
} else if (res.status === 404) {
  console.log('Did not exist');
} else {
  throw new Error('Could not delete');
}

📌 Very common: 204 No Content (without body).

6) Typical status codes (mini "cheat sheet")

  • 200 OK → everything fine (normal GET)
  • 201 Created → created (POST)
  • 204 No Content → ok but without body (DELETE/PUT sometimes)
  • 400 Bad Request → invalid data
  • 401 Unauthorized → not authenticated
  • 403 Forbidden → authenticated but without permissions
  • 404 Not Found → doesn't exist
  • 409 Conflict → conflict (duplicate, version, etc.)
  • 500 → server error

📌 Senior tip: res.ok (200–299) is useful, but sometimes you need to treat 401/403/409 differently.

7) Complete CRUD example with fetch (reusable pattern)

a) Helper to handle errors

async function request(url, options) {
  const res = await fetch(url, {
    headers: { Accept: 'application/json', ...(options?.headers ?? {}) },
    ...options
  });

  // Try to read JSON if it exists
  const contentType = res.headers.get('Content-Type') || '';
  const isJson = contentType.includes('application/json');
  const payload = isJson ? await res.json().catch(() => null) : null;

  if (!res.ok) {
    throw new Error(payload?.message ?? `HTTP Error ${res.status}`);
  }

  return payload; // can be null if 204
}

b) API functions (users)

export const api = {
  listUsers: (query = '') => request(`/api/users${query}`),

  getUser: (id) => request(`/api/users/${id}`),

  createUser: (data) =>
    request('/api/users', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(data)
    }),

  updateUserPut: (id, data) =>
    request(`/api/users/${id}`, {
      method: 'PUT',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(data)
    }),

  updateUserPatch: (id, partial) =>
    request(`/api/users/${id}`, {
      method: 'PATCH',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(partial)
    }),

  deleteUser: (id) =>
    request(`/api/users/${id}`, { method: 'DELETE' })
};

8) Best practices + common errors (the "senior" part)

Best practices

  • Use Accept and Content-Type correctly.
  • Handle important status codes (especially 401/403/409).
  • Separate "API layer" (fetch) from your UI (React components).
  • Use PUT/PATCH with clear intention.

Typical errors

  • Sending PUT with only one field and overwriting the rest of the resource.
  • Forgetting Content-Type: application/json and the server doesn't parse the body.
  • Assuming there's always JSON in the response (eg: 204).
  • Ignoring res.status and not handling cases like 401.
