HTTP Response Codes

Step-by-step guide to understanding what a server responds and why

Step 1: What are HTTP response codes?

Every time you make an HTTP request (from the browser, fetch, Axios, Postman, etc.), the server always responds with a numeric code called a status code.

That code answers a single question:

👉 What happened with the request you just made?

It doesn't matter if the request went well or badly:
the server must always respond with something.

Step 2: The key idea (simple mental model)

Think of HTTP codes as a traffic light:

  • 🟢 2xx → Everything went well
  • 🟡 3xx → Redirection / cache
  • 🔴 4xx → Client error (your request is wrong)
  • 🔥 5xx → Server error (the backend failed)

Just by understanding this, you can debug 80% of errors.

Step 3: HTTP code families

1xx – Informational

You'll rarely see them in normal web development.
They're not relevant to get started.

2xx – Success (the request went well)

All 2xx codes indicate that the operation was successful, but each has a different nuance.

200 OK

The most common.

Means:

"I received your request and processed it correctly".

Typical examples:

  • Get data (GET)
  • Update a resource (PUT)
  • Return information
201 Created

Used when a new resource has been created.

Usually appears when using:

  • POST /users
  • POST /orders

Means:

"Everything went well and I also created something new".

🔑 It's more specific than 200.

204 No Content

The operation was successful, but there's nothing to return.

Typical examples:

  • DELETE /users/123
  • PUT when you don't need to return data

👉 It's normal for the body to be empty.

Step 4: 3xx – Redirects and cache

Not as common in pure APIs, but common on the web.

304 Not Modified

Very important for performance.

Means:

"The resource hasn't changed, use what you already have in cache".

Used with headers like ETag or If-None-Match.

Step 5: 4xx – Client errors (your request is wrong)

Here the server works, but you did something incorrect.

400 Bad Request

The request is malformed.

Examples:

  • Invalid JSON
  • Missing required fields
  • Incorrect data types

👉 The server cannot process what you sent.

401 Unauthorized

You are not authenticated.

Example:

  • Missing token
  • Expired token

👉 It's not a permissions problem, it's that you haven't proven who you are.

403 Forbidden

You are authenticated, but you don't have permission.

Example:

  • Normal user accessing admin endpoint

👉 "I know who you are, but you can't do this".

404 Not Found

The resource doesn't exist.

Example:

  • GET /users/99999 (that user doesn't exist)

👉 The server is fine, the problem is that you're asking for something that doesn't exist.

409 Conflict

Conflict with the current state of the system.

Example:

  • Create a user with an email that already exists

Widely used in real APIs.

422 Unprocessable Entity

The request is correct, but the data doesn't pass validation.

Example:

  • Email with invalid format
  • Password too short

👉 The server understands your request, but can't accept it.

Step 6: 5xx – Server errors (not your fault)

Here the request is well-formed, but the server fails.

500 Internal Server Error

Generic server error.

Example:

  • Unhandled exception
  • Backend bug
503 Service Unavailable

The server is not available.

Example:

  • Maintenance
  • Server down
  • Deploy in progress
504 Gateway Timeout

The intermediary server didn't get a response in time.

Very common with:

  • Proxies
  • Gateways
  • Microservices

Step 7: Relationship between HTTP methods and codes

This is what you'll see most in practice:

  • GET → 200 or 404
  • POST → 201, 400, 409
  • PUT / PATCH → 200 or 204
  • DELETE → 204

Step 8: How an API should respond in case of error

A good backend doesn't just return the code, it also explains the error.

Example error structure:

  • Internal code
  • Clear message
  • Problem details
  • Identifier for logs

This helps a lot for frontend and debugging.

Step 9: Important detail in frontend (typical error)

In JavaScript, fetch does NOT throw errors for 404 or 500.

  • It only fails if there's a network error
  • You must check the status manually

Basic rule:

If response.ok is false, there was an HTTP error.

This is key to handling errors well in the UI.

const res = await fetch('/api/users');

if (!res.ok) {
  // Here you handle 4xx and 5xx errors
  console.error('HTTP Error:', res.status);
  throw new Error(`HTTP Error: ${res.status}`);
}

const data = await res.json();

Step 10: Quick summary to memorize

  • 2xx → Everything fine
  • 4xx → Client error (check your request)
  • 5xx → Server error (not your fault)

Important specific codes:

  • 201 → creates
  • 204 → doesn't return content
  • 401 → not authenticated
  • 403 → no permissions
  • 404 → doesn't exist
