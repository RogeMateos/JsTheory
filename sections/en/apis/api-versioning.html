🔢 API Versioning

Why does API versioning exist?

When an API is already in use by other applications (web, mobile, third parties…), you can't just change it. If you do, you break all applications that depend on it.

👉 Versioning exists to evolve an API without breaking what already works.

📌 The real problem

Imagine this API:

https://example.com/api/resources

Many applications use it and expect:

  • A specific data structure
  • A specific response format
  • Stable behavior

Now the team decides to:

  • Change fields
  • Change names
  • Change business rules

❌ If you modify the API directly, everything stops working.
✅ The solution: version the API

✅ The solution: version the API

Instead of breaking what exists, you create a new version.

Classic example:

https://example.com/api/v1/resources
  • v1 represents the first stable version
  • That version doesn't change
  • Guarantees long-term compatibility

🚀 Evolving without breaking anything

Now the team wants to make important changes (breaking changes).

Instead of modifying v1, they create:

https://example.com/api/v2/resources

Result:

  • v1 keeps working for old apps
  • v2 includes the new changes
  • Each client decides when to update

🔁 Maintaining multiple versions

It's very common for an API to maintain several active versions:

  • /api/v1/... → old applications
  • /api/v2/... → new applications
  • /api/v3/... → future evolution

This allows:

  • Progressive migrations
  • Fewer errors
  • Better developer experience

📐 What an API version guarantees

When you use a specific version (v1, v2…), you know that:

  • The data structure will be the same
  • Fields won't change unexpectedly
  • Behavior is stable
  • It fulfills a contract (API contract)

🧠 Key idea to remember

A versioned API is like a signed contract.
If you want to change the rules, you sign a new contract, you don't break the previous one.

🔧 Common ways to version an API

1️⃣ Version in the URL (most common)

https://api.example.com/v1/users
https://api.example.com/v2/users

✅ Advantages:

  • Very visible and explicit
  • Easy to test in the browser
  • De facto standard in REST

2️⃣ Version in the header

GET https://api.example.com/users
Headers:
  Accept: application/vnd.example.v2+json

✅ Advantages:

  • Clean URL
  • More "pure" according to REST

❌ Disadvantages:

  • Less visible
  • Harder to test manually

3️⃣ Version in query string

https://api.example.com/users?version=2

⚠️ Less common, but seen in some public APIs

📝 Practical example with fetch

Using v1:

const response = await fetch("https://api.example.com/v1/users");
const data = await response.json();

// Expected v1 response:
// { id: 1, name: "John" }

Using v2 (with changes):

const response = await fetch("https://api.example.com/v2/users");
const data = await response.json();

// Expected v2 response:
// { id: 1, firstName: "John", lastName: "Doe" }

👉 Note how v2 changed name to firstName and lastName, but v1 remains the same.

⏰ Deprecation of old versions

Over time, old versions can be deprecated:

  • Deprecation: notification that the version will stop working in X months
  • Sunset: date when the version is definitively shut down

Example of deprecation header:

Deprecation: Sun, 01 Jan 2026 00:00:00 GMT
Sunset: Sun, 01 Jul 2026 00:00:00 GMT

This gives developers time to migrate without surprises.

✅ Quick summary

  • API versioning is very common in production
  • Used to avoid breaking existing applications
  • Normally done in the URL (/v1, /v2)
  • Allows safe API evolution
  • It's a best practice in professional REST APIs
  • Old versions can be deprecated with prior notice

🎯 When to version an API

You should create a new version when:

  • You change the response structure (breaking change)
  • You remove fields that existed before
  • You change the data type of a field
  • You modify expected behavior

❌ A new version is NOT needed when:

  • You add new (optional) fields
  • You fix bugs
  • You improve performance
