🔢 Versionado de APIs (API Versioning)

¿Por qué existe el versionado de una API?

Cuando una API ya está en uso por otras aplicaciones (webs, móviles, terceros…), no se puede cambiar sin más. Si lo haces, rompes todas las aplicaciones que dependen de ella.

👉 El versionado existe para evolucionar una API sin romper lo que ya funciona.

📌 El problema real

Imagina esta API:

https://example.com/api/resources

Muchas aplicaciones la usan y esperan:

  • Una estructura concreta de datos
  • Un formato de respuesta específico
  • Un comportamiento estable

Ahora el equipo decide:

  • Cambiar campos
  • Cambiar nombres
  • Cambiar reglas de negocio

❌ Si modificas la API directamente, todo deja de funcionar.
✅ La solución: versionar la API

✅ La solución: versionar la API

En lugar de romper lo existente, se crea una nueva versión.

Ejemplo clásico:

https://example.com/api/v1/resources
  • v1 representa la primera versión estable
  • Esa versión no cambia
  • Garantiza compatibilidad a largo plazo

🚀 Evolucionar sin romper nada

Ahora el equipo quiere hacer cambios importantes (breaking changes).

En lugar de modificar v1, se crea:

https://example.com/api/v2/resources

Resultado:

  • v1 sigue funcionando para apps antiguas
  • v2 incluye los cambios nuevos
  • Cada cliente decide cuándo actualizar

🔁 Mantener varias versiones

Es muy común que una API mantenga varias versiones activas:

  • /api/v1/... → aplicaciones antiguas
  • /api/v2/... → aplicaciones nuevas
  • /api/v3/... → futura evolución

Esto permite:

  • Migraciones progresivas
  • Menos errores
  • Mejor experiencia para desarrolladores

📐 Qué garantiza una versión de API

Cuando usas una versión concreta (v1, v2…), sabes que:

  • La estructura de datos será la misma
  • Los campos no cambiarán inesperadamente
  • El comportamiento es estable
  • Cumple un contrato (API contract)

🧠 Idea clave para recordar

Una API versionada es como un contrato firmado.
Si quieres cambiar las reglas, firmas un contrato nuevo, no rompes el anterior.

🔧 Formas comunes de versionar una API

1️⃣ Versión en la URL (más común)

https://api.example.com/v1/users
https://api.example.com/v2/users

✅ Ventajas:

  • Muy visible y explícito
  • Fácil de testear en el navegador
  • Estándar de facto en REST

2️⃣ Versión en el header

GET https://api.example.com/users
Headers:
  Accept: application/vnd.example.v2+json

✅ Ventajas:

  • URL limpia
  • Más "pura" según REST

❌ Desventajas:

  • Menos visible
  • Más difícil de probar manualmente

3️⃣ Versión en query string

https://api.example.com/users?version=2

⚠️ Menos común, pero se ve en algunas APIs públicas

📝 Ejemplo práctico con fetch

Usando v1:

const response = await fetch("https://api.example.com/v1/users");
const data = await response.json();

// Respuesta esperada v1:
// { id: 1, name: "John" }

Usando v2 (con cambios):

const response = await fetch("https://api.example.com/v2/users");
const data = await response.json();

// Respuesta esperada v2:
// { id: 1, firstName: "John", lastName: "Doe" }

👉 Nota cómo v2 cambió name por firstName y lastName, pero v1 sigue igual.

⏰ Deprecación de versiones antiguas

Con el tiempo, las versiones antiguas se pueden deprecar:

  • Deprecación: se avisa que la versión dejará de funcionar en X meses
  • Sunset: fecha en la que la versión se apaga definitivamente

Ejemplo de header de deprecación:

Deprecation: Sun, 01 Jan 2026 00:00:00 GMT
Sunset: Sun, 01 Jul 2026 00:00:00 GMT

Esto da tiempo a los desarrolladores para migrar sin sorpresas.

✅ Resumen rápido

  • El versionado de APIs es muy común en producción
  • Se usa para evitar romper aplicaciones existentes
  • Normalmente se hace en la URL (/v1, /v2)
  • Permite evolucionar la API de forma segura
  • Es una buena práctica en APIs REST profesionales
  • Las versiones antiguas se pueden deprecar con aviso previo

🎯 Cuándo versionar una API

Debes crear una nueva versión cuando:

  • Cambias la estructura de respuesta (breaking change)
  • Eliminas campos que existían antes
  • Cambias el tipo de datos de un campo
  • Modificas el comportamiento esperado

❌ NO hace falta nueva versión cuando:

  • Añades campos nuevos (opcionales)
  • Corriges bugs
  • Mejoras el rendimiento
