Crear un POST con fetch

Tutorial paso a paso (como lo harías en un proyecto real)

Paso 0) Qué vas a conseguir

Vas a enviar datos a un servidor para crear un recurso (un "post") usando:

  • fetch(url, { method: "POST", headers, body })
  • JSON.stringify() para convertir tu objeto JS a JSON
  • response.ok + response.json() para manejar la respuesta bien

1) Aclaremos conceptos (para que no haya confusiones)

✅ "JSON" vs "Objeto JavaScript"

  • Objeto JS: vive en memoria { title: '...' }
  • JSON: es un string con un formato concreto '{"title":"..."}'

Por eso en el body del request, casi siempre mandas JSON.stringify(obj).

✅ "Content-Type" no es "content"

  • Header: Content-Type
  • Valor típico: application/json

Ejemplo mental:

  • Content-Type = "te estoy enviando el body en formato JSON"
  • Accept = "prefiero que me respondas en JSON" (opcional pero buena práctica)

2) Entiende la idea: misma URL, distinto método

En una API REST, la URL representa el recurso y el método HTTP representa la acción.

  • GET /posts → listar posts
  • POST /posts → crear un post
  • GET /posts/101 → obtener uno
  • PUT /posts/101 → reemplazar
  • PATCH /posts/101 → actualizar parcial
  • DELETE /posts/101 → borrar

📌 La URL representa un recurso (posts) y el método HTTP representa la acción.

Misma URL, comportamiento distinto por el método.

3) Define la URL del recurso

Usaremos JSONPlaceholder (API de pruebas):

const URL = "https://jsonplaceholder.typicode.com/posts";

4) Crea el objeto "post" en JavaScript (esto NO es JSON todavía)

Normalmente el backend genera el id, así que tú envías lo básico:

const newPost = {
  userId: 1,
  title: "Este es el título de mi post",
  body: "Este es el cuerpo de mi post",
};

¿Por qué no mando el id?

En un POST, normalmente el backend crea el ID (autoincrement / UUID).

En una API real, el backend responde con:

  • el recurso creado
  • y/o un Location header (p.ej. /posts/101)
  • status típico: 201 Created

📌 JSONPlaceholder te devuelve id: 101 por simulación.

5) Convierte ese objeto a JSON para enviarlo en el body

El body de una request HTTP es texto (normalmente).
Para enviar JSON, conviertes tu objeto a string JSON: 

const bodyAsJson = JSON.stringify(newPost);

6) Prepara el fetch con method, headers y body

Por qué headers

"Content-Type": "application/json" significa: "te estoy enviando JSON".

const response = await fetch(URL, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Accept": "application/json",
  },
  body: bodyAsJson,
});

7) Muy importante: controla errores HTTP con response.ok

fetch NO falla solo porque el servidor te responda 400/500.
Tú tienes que comprobarlo. 

if (!response.ok) {
  throw new Error(`HTTP ${response.status} - ${response.statusText}`);
}

Justificación (senior):

  • Si no controlas response.ok, tu app puede tratar como "éxito" una respuesta 400.
  • Esto luego se traduce en bugs de UI ("se creó" cuando no se creó).

8) Lee el JSON de la respuesta (lo que "creó" el servidor)

const createdPost = await response.json();
console.log(createdPost);

9) Código completo (versión buena para tutorial)

async function createPost() {
  const URL = "https://jsonplaceholder.typicode.com/posts";

  const newPost = {
    userId: 1,
    title: "Este es el título de mi post",
    body: "Este es el cuerpo de mi post",
  };

  const response = await fetch(URL, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Accept": "application/json",
    },
    body: JSON.stringify(newPost),
  });

  if (!response.ok) {
    throw new Error(`HTTP ${response.status} - ${response.statusText}`);
  }

  const createdPost = await response.json();
  return createdPost;
}

// Probarlo
createPost()
  .then((data) => console.log("Creado:", data))
  .catch((err) => console.error("Error:", err.message));

10) Qué deberías ver en consola (y por qué sale id: 101)

Verás un objeto como:

  • userId: 1
  • title: ...
  • body: ...
  • id: 101

JSONPlaceholder simula que lo crea y te devuelve un id "nuevo".

11) Nota importante: JSONPlaceholder NO guarda los cambios (API fake)

Aunque te devuelva id: 101, si luego haces GET /posts seguirás viendo hasta el 100.

No es un bug tuyo: es la API de prueba que no persiste datos.

Es una API de pruebas:

  • Responde como si hubiera creado.
  • Pero no escribe realmente en base de datos.
  • Por eso un GET posterior no lo muestra.

12) Validación mínima antes de mandar el POST

La validación no es opcional si quieres calidad:

function validatePostInput(post) {
  if (!post.userId) throw new Error("userId es obligatorio");
  if (!post.title?.trim()) throw new Error("title es obligatorio");
  if (!post.body?.trim()) throw new Error("body es obligatorio");
}

Y lo usas:

validatePostInput(newPost);

Justificación:

Mejor fallar rápido en frontend que mandar basura al backend y esperar.

13) Versión robusta con manejo de errores completo

async function createPostSafe() {
  const URL = "https://jsonplaceholder.typicode.com/posts";

  const newPost = {
    userId: 1,
    title: "Título",
    body: "Cuerpo",
  };

  const response = await fetch(URL, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(newPost),
  });

  // 👇 clave: controlar errores HTTP
  if (!response.ok) {
    // intenta leer body de error si existe
    let errorBody = null;
    try { errorBody = await response.json(); } catch {}
    throw new Error(
      `Error HTTP ${response.status} ${response.statusText} - ${JSON.stringify(errorBody)}`
    );
  }

  return response.json();
}

14) Ejemplo "real" de uso en UI (patrón típico)

Esto ayuda muchísimo a un junior: ver cómo se usa con estados de carga.

async function onSubmit() {
  try {
    setLoading(true);
    setError(null);

    const created = await createPostSafe();
    setResult(created);
  } catch (e) {
    setError(e.message);
  } finally {
    setLoading(false);
  }
}

Justificación:

  • Los requests tienen 3 estados: loading / success / error.
  • Si no modelas esos estados, la UI se vuelve inconsistente.

15) Detalles que elevan el código (extras "senior")

a) Timeout (fetch no trae timeout por defecto)

Un request puede quedarse colgado. Usa AbortController:

async function fetchWithTimeout(url, options = {}, ms = 8000) {
  const controller = new AbortController();
  const id = setTimeout(() => controller.abort(), ms);

  try {
    const response = await fetch(url, {
      ...options,
      signal: controller.signal
    });
    return response;
  } finally {
    clearTimeout(id);
  }
}

b) Seguridad/privacidad

  • No loguear tokens en consola
  • No enviar datos sensibles en logs

c) Headers reales

  • Authorization: Bearer ... (si hay auth)
  • Accept-Language (si i18n)
  • Content-Type correcto

16) Resumen de conceptos clave

  • JSON.stringify() convierte objetos JS a strings JSON
  • Content-Type indica el formato del body
  • response.ok es crucial para detectar errores HTTP
  • Validación temprana evita errores innecesarios
  • Estados UI (loading/error/success) mejoran la experiencia
