Consumir una API en JavaScript con fetch

Guía paso a paso

1. ¿Por qué necesitamos consumir APIs?

En aplicaciones reales (webs, móviles, dashboards, etc.) casi nunca trabajamos solo con datos locales.
Normalmente necesitamos:

  • Datos de un servidor
  • Información de usuarios
  • Listados (posts, productos, pedidos…)
  • Guardar o actualizar información

Todo eso se hace comunicándonos con APIs usando el protocolo HTTP.

2. El problema clave: la asincronía

Cuando una aplicación hace una petición a un servidor:

  • ❌ No queremos bloquear la app
  • ❌ No queremos que la interfaz se quede "congelada"
  • ✅ Queremos que la app siga funcionando mientras llegan los datos

Por eso las peticiones de red en JavaScript son asíncronas.

JavaScript lanza la petición, continúa ejecutando el código y recibe el resultado más tarde.

3. La herramienta nativa: fetch

JavaScript nos ofrece de forma nativa la función fetch para hacer peticiones HTTP.

Ideas clave:

  • fetch inicia una petición de red
  • Devuelve una Promise
  • No bloquea el hilo principal
  • Funciona en navegadores modernos (y en Node con soporte)

Modelo mental:

"Pido algo ahora y prometo manejar la respuesta cuando llegue".

4. API de prueba: JSONPlaceholder

Para aprender no necesitamos crear un backend.
Vamos a usar una API pública y gratuita:

JSONPlaceholder
Una API con datos ficticios para practicar.

Tiene endpoints como:

  • /posts
  • /users
  • /comments
  • /albums

Ejemplo de URL:

https://jsonplaceholder.typicode.com/posts

Si accedes desde el navegador verás:

  • Un JSON
  • Una lista de objetos
  • Datos estructurados con clave–valor

Esto es exactamente lo que consumen las aplicaciones frontend.

5. Primera petición GET con fetch

Vamos a hacer una petición GET para obtener todos los posts.

fetch("https://jsonplaceholder.typicode.com/posts")
  .then(response => {
    console.log(response);
  });

¿Qué es response?

⚠️ Punto importante que muchos juniors no entienden al principio.

response NO son los datos todavía.

Es un objeto que contiene:

  • Código HTTP (status)
  • Headers
  • Información de la petición
  • El cuerpo (body), aún sin procesar

6. Convertir la respuesta a JSON

Como sabemos (por la documentación) que la API devuelve JSON, debemos transformar la respuesta.

fetch("https://jsonplaceholder.typicode.com/posts")
  .then(response => {
    return response.json();
  })
  .then(data => {
    console.log(data);
  });

Qué está pasando aquí

  • fetch → hace la petición
  • Primer then → convierte el body a JSON
  • Segundo then → ya tenemos los datos listos
  • data → es un array de posts

7. ¿Por qué response.json() devuelve una Promise?

Porque:

  • Leer el body es un proceso asíncrono
  • Puede fallar (JSON inválido, body vacío, etc.)

Regla mental:

Cada paso asíncrono devuelve una Promise.

8. Manejo de errores (muy importante)

Error común

Muchos creen que:

"Si el servidor responde 404 o 500, entra en catch".

❌ Eso no es cierto.

fetch solo entra en catch si:

  • Hay un error de red
  • Problema de conexión
  • CORS bloqueado
  • La petición se cancela

Los errores HTTP NO lanzan error automáticamente.

9. Forma correcta de manejar errores HTTP

Debemos comprobar response.ok.

fetch("https://jsonplaceholder.typicode.com/posts")
  .then(response => {
    if (!response.ok) {
      throw new Error(`HTTP error ${response.status}`);
    }
    return response.json();
  })
  .then(data => {
    console.log("Datos:", data);
  })
  .catch(error => {
    console.error("Error:", error);
  });

Qué conseguimos con esto

  • Convertimos errores HTTP en errores reales
  • El catch ahora sí captura fallos importantes
  • Código más profesional y predecible

10. Versión recomendada hoy: async / await

Para la mayoría de personas, esta forma es más legible y clara.

async function getPosts() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/posts");

    if (!response.ok) {
      throw new Error(`HTTP error ${response.status}`);
    }

    const data = await response.json();
    console.log(data);
    return data;

  } catch (error) {
    console.error("Error:", error);
  }
}

getPosts();

Ventajas de async/await

  • Código más lineal
  • Más fácil de leer
  • Más fácil de depurar
  • Ideal para proyectos reales y React

11. Peticiones POST (crear datos)

Hasta ahora solo hemos leído datos.
Vamos a enviar información al servidor.

async function createPost() {
  const response = await fetch(
    "https://jsonplaceholder.typicode.com/posts",
    {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        title: "Mi primer post",
        body: "Contenido del post",
        userId: 1,
      }),
    }
  );

  const data = await response.json();
  console.log(data);
}

createPost();

Detalles importantes

  • method: tipo de petición HTTP
  • headers: describen el formato de los datos
  • body: siempre string (normalmente JSON)

12. Cancelar peticiones (caso real en aplicaciones)

Ejemplo típico:

  • Usuario cambia de página
  • Usuario escribe rápido en un buscador
  • Ya no necesitamos la respuesta anterior
const controller = new AbortController();

fetch("https://jsonplaceholder.typicode.com/posts", {
  signal: controller.signal,
})
  .then(response => response.json())
  .then(data => console.log(data))
  .catch(error => {
    if (error.name === "AbortError") {
      console.log("Petición cancelada");
    }
  });

// Cancelar la petición
controller.abort();

Esto es muy común en interfaces modernas.

13. Buenas prácticas finales

  • ✔️ Usa siempre la documentación de la API
  • ✔️ Comprueba response.ok
  • ✔️ Maneja errores correctamente
  • ✔️ Usa async/await cuando sea posible
  • ✔️ Mira la pestaña Network en DevTools
  • ✔️ No asumas la estructura de los datos

14. Resumen mental final

Cuando consumes una API con fetch:

  1. Haces la petición
  2. Recibes una respuesta
  3. Validás el estado HTTP
  4. Transformas los datos (JSON)
  5. Procesas la información
  6. Manejas errores

Si entiendes este flujo, entiendes el 80% del consumo de APIs en frontend.
