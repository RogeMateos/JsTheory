Códigos de respuesta HTTP

Guía paso a paso para entender qué responde un servidor y por qué

Paso 1: ¿Qué son los códigos de respuesta HTTP?

Cada vez que haces una petición HTTP (desde el navegador, fetch, Axios, Postman, etc.), el servidor siempre responde con un código numérico llamado status code.

Ese código responde a una sola pregunta:

👉 ¿Qué ha pasado con la petición que acabas de hacer?

No importa si la petición ha ido bien o mal:
el servidor siempre debe contestar algo.

Paso 2: La idea clave (modelo mental sencillo)

Piensa en los códigos HTTP como un semáforo:

  • 🟢 2xx → Todo ha ido bien
  • 🟡 3xx → Redirección / caché
  • 🔴 4xx → Error del cliente (tu petición está mal)
  • 🔥 5xx → Error del servidor (el backend ha fallado)

Con solo entender esto, ya puedes depurar el 80% de los errores.

Paso 3: Las familias de códigos HTTP

1xx – Informativos

Raramente los verás en desarrollo web normal.
No son relevantes para empezar.

2xx – Éxito (la petición ha ido bien)

Todos los códigos 2xx indican que la operación ha sido correcta, pero cada uno tiene un matiz distinto.

200 OK

El más común.

Significa:

"He recibido tu petición y la he procesado correctamente".

Ejemplos típicos:

  • Obtener datos (GET)
  • Actualizar un recurso (PUT)
  • Devolver información
201 Created

Se usa cuando se ha creado un nuevo recurso.

Normalmente aparece al usar:

  • POST /users
  • POST /orders

Significa:

"Todo ha ido bien y además he creado algo nuevo".

🔑 Es más específico que 200.

204 No Content

La operación ha sido correcta, pero no hay nada que devolver.

Ejemplos típicos:

  • DELETE /users/123
  • PUT cuando no necesitas devolver datos

👉 Es normal que el body esté vacío.

Paso 4: 3xx – Redirecciones y caché

No son tan comunes en APIs puras, pero sí en web.

304 Not Modified

Muy importante para rendimiento.

Significa:

"El recurso no ha cambiado, usa lo que ya tienes en caché".

Se usa con headers como ETag o If-None-Match.

Paso 5: 4xx – Errores del cliente (tu petición está mal)

Aquí el servidor funciona, pero tú has hecho algo incorrecto.

400 Bad Request

La petición está mal formada.

Ejemplos:

  • JSON inválido
  • Campos obligatorios faltantes
  • Tipos de datos incorrectos

👉 El servidor no puede procesar lo que enviaste.

401 Unauthorized

No estás autenticado.

Ejemplo:

  • Falta el token
  • Token expirado

👉 No es un problema de permisos, es que no has demostrado quién eres.

403 Forbidden

Estás autenticado, pero no tienes permiso.

Ejemplo:

  • Usuario normal accediendo a endpoint de admin

👉 "Sé quién eres, pero no puedes hacer esto".

404 Not Found

El recurso no existe.

Ejemplo:

  • GET /users/99999 (no existe ese usuario)

👉 El servidor está bien, el problema es que pides algo que no existe.

409 Conflict

Conflicto con el estado actual del sistema.

Ejemplo:

  • Crear un usuario con un email que ya existe

Muy usado en APIs reales.

422 Unprocessable Entity

La petición es correcta, pero los datos no pasan validación.

Ejemplo:

  • Email con formato inválido
  • Password demasiado corto

👉 El servidor entiende tu petición, pero no puede aceptarla.

Paso 6: 5xx – Errores del servidor (no es tu culpa)

Aquí la petición está bien hecha, pero el servidor falla.

500 Internal Server Error

Error genérico del servidor.

Ejemplo:

  • Excepción no controlada
  • Bug en el backend
503 Service Unavailable

El servidor no está disponible.

Ejemplo:

  • Mantenimiento
  • Servidor caído
  • Deploy en curso
504 Gateway Timeout

El servidor intermediario no obtuvo respuesta a tiempo.

Muy común con:

  • Proxies
  • Gateways
  • Microservicios

Paso 7: Relación entre métodos HTTP y códigos

Esto es lo que más verás en la práctica:

  • GET → 200 o 404
  • POST → 201, 400, 409
  • PUT / PATCH → 200 o 204
  • DELETE → 204

Paso 8: Cómo debería responder una API en caso de error

Un buen backend no solo devuelve el código, también explica el error.

Ejemplo de estructura de error:

  • Código interno
  • Mensaje claro
  • Detalles del problema
  • Identificador para logs

Esto ayuda muchísimo al frontend y al debugging.

Paso 9: Detalle importante en frontend (error típico)

En JavaScript, fetch NO lanza errores por 404 o 500.

  • Solo falla si hay error de red
  • Debes comprobar el status manualmente

Regla básica:

Si response.ok es false, hubo un error HTTP.

Esto es clave para manejar bien errores en la UI.

const res = await fetch('/api/users');

if (!res.ok) {
  // Aquí manejas errores 4xx y 5xx
  console.error('Error HTTP:', res.status);
  throw new Error(`HTTP Error: ${res.status}`);
}

const data = await res.json();

Paso 10: Resumen rápido para memorizar

  • 2xx → Todo bien
  • 4xx → Error del cliente (revisa tu request)
  • 5xx → Error del servidor (no es tu culpa)

Códigos específicos importantes:

  • 201 → crea
  • 204 → no devuelve contenido
  • 401 → no autenticado
  • 403 → sin permisos
  • 404 → no existe
