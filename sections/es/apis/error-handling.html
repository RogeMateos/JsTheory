Manejo correcto de errores con fetch en JavaScript

Cuando empezamos a consumir APIs con fetch, hay un detalle clave que suele confundir mucho:

Un 404 o un 500 NO hacen que fetch entre automáticamente en el catch.

Vamos a entender por qué ocurre, qué significa realmente un error en fetch y cómo manejarlo bien en aplicaciones reales.

1. El problema real (lo que suele sorprender)

Imagina que llamas a una URL que no existe:

fetch("https://api.ejemplo.com/pats")
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => console.error("Error:", err));

Esperas que entre en el catch…
pero no entra, aunque el servidor responda 404.

❓ ¿Por qué?

2. Cómo funciona fetch realmente

fetch solo rechaza la promesa cuando ocurre un error técnico de red, por ejemplo:

  • No hay conexión a internet
  • DNS incorrecto
  • Servidor inaccesible
  • CORS bloqueado por el navegador

Pero si el servidor responde, aunque sea con:

  • 404 Not Found
  • 401 Unauthorized
  • 500 Internal Server Error

👉 Para fetch, eso es una respuesta válida.

Por eso:

  • ❌ 404 no es un error para fetch
  • ✅ Es una respuesta HTTP con un código que tú debes evaluar

3. Inspeccionando la respuesta

Cuando fetch responde, tienes información muy útil:

const response = await fetch(url);

console.log(response.status); // 200, 404, 500...
console.log(response.ok);     // true si 200–299

response.ok

  • true → código entre 200 y 299
  • false → cualquier otro código (404, 401, 500…)

👉 Esta propiedad existe precisamente para manejar errores HTTP.

4. La solución correcta: convertir HTTP errors en errores reales

Si un código no es válido para tu aplicación, lanza un error tú mismo.

const response = await fetch(url);

if (!response.ok) {
  throw new Error(`HTTP Error ${response.status}`);
}

const data = await response.json();
return data;

¿Qué ganamos?

  • Flujo limpio cuando todo va bien
  • Centralizamos errores en el catch
  • Control total sobre qué consideramos "error"

5. Ejemplo completo con try / catch

async function getPosts() {
  try {
    const response = await fetch("https://api.ejemplo.com/posts");

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const data = await response.json();
    console.log("Datos:", data);

  } catch (error) {
    console.error("Algo salió mal:", error.message);
  }
}

👉 Ahora sí:

  • 404 → entra en catch
  • 500 → entra en catch
  • Error de red → entra en catch

6. Versión más profesional (patrón senior)

En proyectos reales, conviene crear un helper reutilizable.

async function fetchJson(url, options = {}) {
  const response = await fetch(url, options);

  let body = null;
  const contentType = response.headers.get("content-type") || "";

  if (contentType.includes("application/json")) {
    try {
      body = await response.json();
    } catch {}
  } else {
    try {
      body = await response.text();
    } catch {}
  }

  if (!response.ok) {
    const error = new Error(`Request failed: ${response.status}`);
    error.status = response.status;
    error.url = response.url;
    error.body = body;
    throw error;
  }

  return body;
}

¿Por qué es mejor?

  • Conserva información del error
  • Sirve para todas las APIs
  • Facilita mensajes claros en la UI

7. Manejo del error en la interfaz

try {
  const posts = await fetchJson("/posts");
  render(posts);
} catch (e) {
  if (e.status === 404) showMessage("Recurso no encontrado");
  else if (e.status === 401) showMessage("No autorizado");
  else if (e.status >= 500) showMessage("Error del servidor");
  else showMessage("Error inesperado");
}

👉 No todos los errores se muestran igual al usuario.

8. Casos importantes que debes conocer

204 No Content

  • Respuesta válida
  • ❌ No llames a response.json() (no hay body)

JSON inválido

  • Algunas APIs devuelven HTML en errores
  • Siempre protege la lectura del body

CORS

  • El navegador puede bloquear la respuesta
  • Parece error de red, aunque el servidor sí responda

9. Resumen clave (para que se quede grabado)

fetch solo falla si falla la red.
Los errores HTTP (404, 500…) son respuestas válidas y debes gestionarlas tú con response.ok.
