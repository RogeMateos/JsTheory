Autenticación en APIs REST: API Key, Bearer Token y JWT

Tutorial paso a paso

Objetivo

Entender cómo se autentican muchas APIs modernas y cómo enviar credenciales correctamente desde JavaScript (fetch), evitando errores típicos y agujeros de seguridad.

1) Primero: Autenticación vs Autorización (base mental)

Antes de hablar de keys y tokens, grábate esto:

  • Autenticación (AuthN): ¿Quién eres?
  • Autorización (AuthZ): ¿Qué puedes hacer?

Ejemplo rápido:

  • Te logueas → autenticación ✅
  • Intentas ver /admin → autorización ✅/❌ según rol

2) ¿Por qué una API necesita autenticación?

Porque la API debe poder:

  • Proteger recursos (datos privados)
  • Aplicar permisos (roles/scopes)
  • Limitar abuso (rate limiting)
  • Identificar al cliente o usuario

Sin autenticación, cualquiera podría llamar endpoints sensibles.

3) API Key: qué es y cuándo se usa

Qué es

Una API Key es una cadena de texto que identifica a un cliente (app/proyecto).

Ejemplo (ficticio):

X-API-Key: 123abc...

Cuándo tiene sentido

✅ Útil para:

  • APIs públicas con cuotas
  • Identificar la aplicación (no necesariamente usuario final)
  • Server-to-server (backend con backend)

Riesgo típico

❌ Si la pones en el frontend, se puede copiar (DevTools, red, etc.).
Así que una API Key en frontend no puede ser "secreto real", solo control de cuota/uso.

4) ¿Dónde enviar credenciales? (lo importante)

Nunca en la URL

Evita cosas como:

https://api.com/data?apiKey=MI_KEY

Porque la URL se filtra fácil en:

  • Historial del navegador
  • Logs
  • Analytics
  • Proxies
  • Headers Referer

Lo correcto: headers (o cookies)

La práctica estándar es usar headers para tokens:

Authorization: Bearer <token>

5) Token: qué es en la vida real

Un token suele ser un string que representa una sesión/usuario o permiso.

Hay dos grandes tipos:

  • Token opaco: no lo "entiendes" tú, lo entiende el servidor.
  • JWT: token con estructura (lo ves y tiene claims).

En ambos casos, lo normal es enviarlo en el header Authorization usando Bearer.

Nota: no es "beer token", es Bearer token.

6) Bearer Token: el estándar práctico

"Bearer" significa:

Si presentas este token, te trato como el usuario/cliente asociado.

Ejemplo HTTP:

Authorization: Bearer eyJhbGciOi...

7) JWT: qué es y qué NO es

Qué significa

JWT = JSON Web Token

Suele tener 3 partes separadas por puntos:

header.payload.signature

Ejemplo:

xxxxx.yyyyy.zzzzz

JWT normalmente está firmado, no cifrado

Aquí se confunde mucha gente:

  • ✅ Firmado (signature): evita que lo manipulen sin que el servidor lo note.
  • ❌ No es cifrado por defecto: el payload se puede leer (base64).

Regla de oro:

No metas secretos en el payload del JWT.

Por qué se usa JWT

Porque puedes incluir datos útiles (claims), como:

  • id de usuario
  • roles/scopes
  • expiración exp

Y el servidor puede validar la firma sin ir siempre a base de datos (según arquitectura).

8) Ejemplo: consumir una API con Bearer token (fetch)

Imagina que ya tienes un token (por login u OAuth). Llamas a un endpoint protegido:

const token = getAccessToken(); // idealmente desde memoria
const res = await fetch("https://api.miapp.com/profile", {
  headers: {
    Authorization: `Bearer ${token}`,
  },
});

if (!res.ok) throw new Error("No autorizado o error");
const data = await res.json();
console.log(data);

9) Flujo completo típico (el ciclo real de autenticación)

Paso A: Login

  1. Usuario mete credenciales
  2. Backend valida
  3. Backend devuelve un access token (y a veces refresh token)

Paso B: Requests protegidas

En cada request:

  1. El frontend manda Authorization: Bearer <accessToken>
  2. El backend valida el token
  3. Responde 200 si ok, 401 si no

Paso C: Token expirado

Si expira:

  1. Pides uno nuevo con refresh token
  2. Repites la request

10) Access token vs Refresh token (muy común en sistemas modernos)

Access token

  • Dura poco (minutos)
  • Se manda siempre en Authorization

Refresh token

  • Dura más (días/semanas)
  • Se usa para pedir nuevos access tokens
  • Suele guardarse en cookie HttpOnly (más seguro)

Ventaja:

Si roban el access token, el daño es limitado por tiempo.

11) Manejo básico de 401 (expiración) en fetch

Versión simple: si 401, intentas refrescar y reintentas.

async function fetchWithAuth(url, options = {}) {
  const token = getAccessToken();

  let res = await fetch(url, {
    ...options,
    headers: {
      ...(options.headers || {}),
      Authorization: `Bearer ${token}`,
    },
  });

  if (res.status !== 401) return res;

  // 401 -> token expirado o inválido
  const refreshed = await refreshAccessToken();
  if (!refreshed) throw new Error("Sesión expirada. Vuelve a iniciar sesión.");

  const newToken = getAccessToken();
  return fetch(url, {
    ...options,
    headers: {
      ...(options.headers || {}),
      Authorization: `Bearer ${newToken}`,
    },
  });
}

refreshAccessToken() normalmente llama a /auth/refresh y el refresh token va en cookie HttpOnly.

12) Dónde guardar tokens (decisión práctica)

Esto marca la diferencia entre "funciona" y "es seguro".

Opción recomendada (patrón común)

  • Access token en memoria (no localStorage)
  • Refresh token en cookie HttpOnly + Secure

✅ Reduce robo por XSS
⚠️ Requiere endpoint refresh bien diseñado

Opción simple (pero más peligrosa)

  • Access token en localStorage

✅ Fácil
❌ Si hay XSS, te lo roban

13) Checklist de buenas prácticas (nivel senior)

  • ✅ HTTPS siempre
  • ✅ Nunca tokens en URL
  • ✅ Access token con expiración corta
  • ✅ Refresh token con rotación y revocación
  • ✅ No guardar secretos en JWT payload
  • ✅ Scopes/roles claros
  • ✅ Rate limiting en backend
  • ✅ Logs sin filtrar tokens
  • ✅ Manejar bien 401/403:
    • 401: no autenticado / token inválido
    • 403: autenticado pero sin permisos

14) Resumen final

  • API Key: identifica la app (no ideal para usuario final; en frontend no es secreta).
  • Bearer token: forma estándar de mandar tokens en Authorization.
  • JWT: token con claims, normalmente firmado (no cifrado), útil para auth distribuida.
  • Lo correcto: tokens en headers (o cookies), nunca en URL.
  • Profesional: access token corto + refresh token para renovar.
