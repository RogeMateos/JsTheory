HTTP y Métodos (GET, POST, PUT, PATCH, DELETE) para APIs

1) Qué es HTTP (modelo mental request/response)

HTTP es el "idioma" que usan cliente (navegador/app) y servidor para hablar.

  • El cliente envía una request (petición).
  • El servidor devuelve una response (respuesta).

Ejemplo mental:

Request

  • Método: GET
  • URL: /users/42
  • Headers: Accept: application/json

Response

  • Status: 200 OK
  • Headers: Content-Type: application/json
  • Body: { "id": 42, "name": "Roge" }

📌 Idea clave: HTTP no es "solo para webs", es para cualquier comunicación cliente-servidor.

2) URL: path y query params (lo que "pides" y cómo lo filtras)

Una URL suele tener:

  • Path: el recurso que quieres (/users, /users/42)
  • Query params: filtros/paginación (?role=admin&page=2)

Ejemplos:

  • GET /users → "dame todos los usuarios"
  • GET /users/42 → "dame el usuario 42"
  • GET /users?role=admin&page=2 → "dame admins, página 2"

📌 Regla práctica: los query params se usan mucho en GET para buscar/filtrar sin enviar body.

3) Partes de una request (qué viaja del cliente al servidor)

Una request suele incluir:

a) Método

Define la intención:

  • GET → leer
  • POST → crear/acción
  • PUT → reemplazar
  • PATCH → modificar parcialmente
  • DELETE → eliminar

b) Headers (metadatos)

Los más típicos:

  • Accept: qué formato esperas recibir (ej: JSON)
  • Content-Type: qué formato envías (ej: JSON)
  • Authorization: token/cookies (si aplica)

c) Body (contenido)

Solo en métodos que envían datos (POST/PUT/PATCH).
En GET normalmente no se manda body.

4) Partes de una response (lo que vuelve del servidor)

Una response trae:

a) Status code (lo más importante)

Te dice si salió bien o qué falló.

b) Headers

Ej: Content-Type: application/json

c) Body

Puede ser JSON, HTML o vacío (por ejemplo en 204).

5) Métodos HTTP (con ejemplos reales)

Usaremos un recurso típico: users

Convención REST común:

  • Colección: /users
  • Elemento: /users/:id

5.1 GET (leer datos)

Se usa para obtener información.
No debería cambiar nada en el servidor.

Ejemplos:

  • GET /users (lista)
  • GET /users/42 (detalle)
  • GET /users?role=admin&page=2 (filtro/paginación)

Ejemplo con fetch:

const res = await fetch('/api/users?role=admin&page=2', {
  headers: { Accept: 'application/json' }
});

if (!res.ok) throw new Error('Error al cargar usuarios');

const users = await res.json();
console.log(users);

5.2 POST (crear recurso o ejecutar una acción)

Se usa para:

  • Crear un nuevo recurso en una colección: POST /users
  • O ejecutar acciones no idempotentes: POST /login, POST /payments

Ejemplo: crear usuario

const res = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Ana', email: 'ana@mail.com' })
});

if (res.status === 201) {
  const createdUser = await res.json();
  console.log('Creado:', createdUser);
} else {
  const error = await res.json().catch(() => null);
  throw new Error(error?.message ?? 'No se pudo crear');
}

📌 Nota senior: si creas, lo típico es 201 Created.

5.3 PUT vs PATCH (la diferencia que más bugs evita)

PUT = reemplazo completo (conceptualmente)

"Te envío el recurso entero y tú lo dejas así".

PUT /users/42

await fetch('/api/users/42', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    id: 42,
    name: 'Roge',
    email: 'roge@mail.com',
    role: 'admin'
  })
});

✅ Útil cuando tu UI edita "el formulario completo".

PATCH = actualización parcial (muy común en frontend)

"Te envío solo lo que cambia".

PATCH /users/42

await fetch('/api/users/42', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ role: 'admin' })
});

📌 Regla práctica:

  • Si mandas todo: PUT
  • Si mandas solo lo modificado: PATCH

5.4 DELETE (eliminar)

DELETE /users/42

const res = await fetch('/api/users/42', { method: 'DELETE' });

if (res.status === 204) {
  console.log('Eliminado');
} else if (res.status === 404) {
  console.log('No existía');
} else {
  throw new Error('No se pudo eliminar');
}

📌 Muy común: 204 No Content (sin body).

6) Status codes típicos (mini "chuleta")

  • 200 OK → todo bien (GET normal)
  • 201 Created → creado (POST)
  • 204 No Content → ok pero sin body (DELETE/PUT a veces)
  • 400 Bad Request → datos inválidos
  • 401 Unauthorized → no autenticado
  • 403 Forbidden → autenticado pero sin permisos
  • 404 Not Found → no existe
  • 409 Conflict → conflicto (duplicado, versión, etc.)
  • 500 → error del servidor

📌 Senior tip: res.ok (200–299) es útil, pero a veces necesitas tratar 401/403/409 distinto.

7) Ejemplo completo CRUD con fetch (patrón reutilizable)

a) Helper para manejar errores

async function request(url, options) {
  const res = await fetch(url, {
    headers: { Accept: 'application/json', ...(options?.headers ?? {}) },
    ...options
  });

  // Intentar leer JSON si existe
  const contentType = res.headers.get('Content-Type') || '';
  const isJson = contentType.includes('application/json');
  const payload = isJson ? await res.json().catch(() => null) : null;

  if (!res.ok) {
    throw new Error(payload?.message ?? `HTTP Error ${res.status}`);
  }

  return payload; // puede ser null si 204
}

b) Funciones de API (users)

export const api = {
  listUsers: (query = '') => request(`/api/users${query}`),

  getUser: (id) => request(`/api/users/${id}`),

  createUser: (data) =>
    request('/api/users', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(data)
    }),

  updateUserPut: (id, data) =>
    request(`/api/users/${id}`, {
      method: 'PUT',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(data)
    }),

  updateUserPatch: (id, partial) =>
    request(`/api/users/${id}`, {
      method: 'PATCH',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(partial)
    }),

  deleteUser: (id) =>
    request(`/api/users/${id}`, { method: 'DELETE' })
};

8) Buenas prácticas + errores comunes (la parte "senior")

Buenas prácticas

  • Usa Accept y Content-Type correctamente.
  • Trata status codes importantes (sobre todo 401/403/409).
  • Separa "capa API" (fetch) de tu UI (React components).
  • Usa PUT/PATCH con intención clara.

Errores típicos

  • Mandar PUT con solo un campo y pisar el resto del recurso.
  • Olvidar Content-Type: application/json y el servidor no parsea el body.
  • Asumir que siempre hay JSON en la respuesta (ej: 204).
  • Ignorar res.status y no manejar casos como 401.
