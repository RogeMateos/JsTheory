Patrón Singleton en JavaScript

1) ¿Qué es un patrón de diseño?

Un patrón de diseño es una "receta" o solución repetible para problemas comunes de diseño de software.

  • No es una librería
  • No es una regla obligatoria
  • Es una forma conocida de resolver algo que suele repetirse

2) ¿Qué problema resuelve Singleton?

Singleton busca esto:

  • ✅ Que solo exista una única instancia de una clase durante la ejecución del programa
  • ✅ Y normalmente también ofrece un punto único de acceso a esa instancia

Ejemplos típicos donde sí tiene sentido:

  • Logger (registro de logs)
  • Configuración global (solo lectura)
  • Cache
  • Cliente de API / DB (con cuidado)

3) Caso base: clase normal (NO Singleton)

Vamos a simular una "sesión" muy simple.


class Session {
  constructor(username) {
    this.user = username;
  }
}

const s1 = new Session("Bryce");
const s2 = new Session(); // otra instancia distinta

console.log(s1.user); // "Bryce"
console.log(s2.user); // undefined
console.log(s1 === s2); // false

🔴 Problema

Si tu app crea sesiones en distintos sitios, vas a tener instancias diferentes y el estado puede ser inconsistente.

4) Singleton (versión recomendada): getInstance()

Esta es la forma más clara para un junior porque no hay magia en el constructor.

Paso 4.1: Creamos la clase con una instancia "guardada"

Usamos una propiedad estática privada para guardar la instancia única:


class Session {
  static #instance = null; // aquí guardaremos la única instancia
  user = null;

  constructor() {
    // constructor normal (sin trucos)
  }
}

Paso 4.2: Creamos el punto de acceso global getInstance()


class Session {
  static #instance = null;
  user = null;

  constructor() {}

  static getInstance() {
    // Si NO existe, la creamos
    if (!Session.#instance) {
      Session.#instance = new Session();
    }
    // Si existe, devolvemos la misma
    return Session.#instance;
  }
}

✅ Ya tenemos singleton

Siempre devolverá la misma instancia.

5) Añadimos comportamiento real: login, leer usuario, limpiar


class Session {
  static #instance = null;
  user = null;

  constructor() {}

  static getInstance() {
    if (!Session.#instance) {
      Session.#instance = new Session();
    }
    return Session.#instance;
  }

  login(username) {
    this.user = username;
  }

  clear() {
    this.user = null;
  }
}

6) Probamos que funciona (la demo clave)


const s1 = Session.getInstance();
s1.login("Bryce");

const s2 = Session.getInstance();

console.log(s1.user); // "Bryce"
console.log(s2.user); // "Bryce"
console.log(s1 === s2); // true ✅ misma instancia

✅ Esto demuestra el concepto

Da igual cuántas veces accedas, siempre es la misma instancia.

7) "Reset" para tests o para reiniciar totalmente

En tests es común querer "empezar limpio". Podemos añadir un método estático para resetear:


class Session {
  static #instance = null;
  user = null;

  constructor() {}

  static getInstance() {
    if (!Session.#instance) {
      Session.#instance = new Session();
    }
    return Session.#instance;
  }

  login(username) {
    this.user = username;
  }

  clear() {
    this.user = null;
  }

  static resetForTests() {
    Session.#instance = null;
  }
}

Uso:


Session.resetForTests();
const s = Session.getInstance();
console.log(s.user); // null

8) Versión alternativa (clásica): "return en el constructor"

Esto se ve mucho en ejemplos antiguos. Funciona, pero confunde más.


class Session {
  static instance = null;

  constructor(username) {
    if (Session.instance) return Session.instance;

    this.user = username;
    Session.instance = this;
  }
}

const s1 = new Session("Bryce");
const s2 = new Session("Otro");

console.log(s1.user); // "Bryce"
console.log(s2.user); // "Bryce" (ignora "Otro")
console.log(s1 === s2); // true

⚠️ Importante

La segunda vez que haces new Session("Otro"), ese parámetro se ignora porque te devuelve la instancia anterior.

9) La forma más común en JS moderno: Singleton por módulo

En proyectos reales, muchas veces haces esto:


// session.js
class Session {
  user = null;
  login(name) { this.user = name; }
  clear() { this.user = null; }
}

export const session = new Session();

✅ Ventaja

Como los módulos se cachean, session será el mismo objeto para quien lo importe.

10) Cuándo NO usar Singleton (lección senior)

Singleton puede ser mala idea cuando:

  • Necesitas testear fácil (estado global rompe tests)
  • Tienes múltiples usuarios concurrentes (backend)
  • Quieres código desacoplado (inyección de dependencias suele ser mejor)

⚠️ Backend warning

En Node/Express, un singleton vive en el proceso, así que NO guardes "usuario actual" global o mezclarás usuarios.

✅ Resumen

Lo que debes recordar

  • Singleton = una sola instancia
  • Ideal para recursos globales (logger, config, cache)
  • En JS moderno: getInstance() o singleton por módulo
  • Evítalo si te mete estado global difícil de testear o si es estado "por usuario"

Checklist de Errores Comunes

⚠️ Errores típicos a evitar

  • ❌ Usar singleton para estado "por usuario" en backend
  • ❌ No proporcionar un método de reset para tests
  • ❌ Abusar del patrón cuando inyección de dependencias sería mejor
  • ❌ No documentar que una clase es singleton
